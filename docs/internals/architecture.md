# Architecture Overview

A system map for contributors and maintainers. Read this before changing code: it
names the real subsystems under `src/`, shows how they layer, and traces the
end-to-end change lifecycle through the code that implements it.

This is the **contributor-facing** architecture doc. It is distinct from the
generated `docs/architecture.md` (which is regenerated by `DocGenerator` and
describes the *user's* project, not metta's own internals). Do not confuse the two.

> **Related internals docs:** [data-model.md](./data-model.md) (Zod schemas and
> on-disk state shapes), [extending.md](./extending.md) (adding workflows, gates,
> agents, skills), [guard-hooks.md](./guard-hooks.md) (the skill-enforcement
> PreToolUse hook). For the conceptual workflow walkthroughs see
> [`../workflows/`](../workflows/).

## Subsystem inventory

Every subsystem lives in its own directory under `src/` and is re-exported from
the barrel at `src/index.ts`. The lead file named below is the entry point worth
reading first.

| Subsystem | Dir | Lead file | Responsibility |
|-----------|-----|-----------|----------------|
| schemas | `src/schemas/` | `index.ts` | Zod schemas + inferred types for every state file, config, workflow, gate, and artifact. The validation backbone — nothing is read or written without a schema. |
| state | `src/state/` | `state-store.ts` | Generic schema-validated YAML reader/writer with stale-lock handling (`StateStore`). The lowest-level I/O primitive every store builds on. |
| config | `src/config/` | `config-loader.ts` | Loads + deep-merges project / user `metta.yaml` config (`ConfigLoader`); `config-writer.ts` and `repair-config.ts` mutate and heal it. |
| providers | `src/providers/` | `provider.ts` | `AIProvider` interface (`generateText` / `generateObject` / `streamText`); `anthropic-provider.ts` is the Anthropic SDK implementation. |
| workflow | `src/workflow/` | `workflow-engine.ts` | Loads workflow YAML, resolves `extends`, topologically sorts artifact dependencies into a `buildOrder`, detects cycles (`WorkflowEngine`). |
| artifacts | `src/artifacts/` | `artifact-store.ts` | Creates changes (slug + metadata), tracks per-artifact status (`pending`/`ready`/`in_progress`/`complete`/`failed`/`skipped`), promotes the workflow forward, archives on finalize (`ArtifactStore`). |
| specs | `src/specs/` | `spec-parser.ts`, `spec-lock-manager.ts` | Markdown spec + delta-spec parsing (remark), requirement hashing, and the `spec.lock` version ledger (`SpecLockManager`) used for merge conflict detection. |
| context | `src/context/` | `context-engine.ts` | Resolves per-artifact context manifests, loads + token-budgets files (`ContextEngine`); `token-counter.ts` counts, `instruction-generator.ts` renders instruction-mode prompts. |
| execution | `src/execution/` | `execution-engine.ts` | Runs task batches sequentially or in parallel git worktrees (`ExecutionEngine`); `batch-planner.ts` (pure batching), `worktree-manager.ts` (git I/O), `fan-out.ts` (multi-perspective parallel work). |
| gates | `src/gates/` | `gate-registry.ts` | Loads gate definitions from YAML and runs their shell commands with timeout/process-group kill (`GateRegistry`). The quality enforcement layer. |
| finalize | `src/finalize/` | `finalizer.ts` | Orchestrates finalize: spec-merge → gates → docs → archive (`Finalizer`); `spec-merger.ts` (pure delta merge + conflict detection), `finalize-lock.ts` (PID-aware concurrency lock). |
| ship | `src/ship/` | `merge-safety.ts` | Defense-in-depth merge to main: snapshot tag, pre-merge gates, conflict detection, recorded steps (`MergeSafetyResult`). |
| planning | `src/planning/` | `tasks-md-parser.ts` | Parses `tasks.md` into task definitions; `parallel-wave-computer.ts` computes parallelizable execution waves. |
| complexity | `src/complexity/` | `scorer.ts` | Scores change complexity (`scorer.ts`) from file counts (`file-count-parser.ts`) and renders the tier recommendation (`renderer.ts`). Drives adaptive tier selection. |
| stories | `src/stories/` | `story-validator.ts` | Validates user-story artifacts (priority, acceptance criteria) for the story layer of the spec format. |
| constitution | `src/constitution/` | `checker.ts` | Checks a change spec against the project constitution's Conventions / Off-Limits (`checker.ts`, `constitution-parser.ts`, `complexity-tracking.ts`). |
| discovery | `src/discovery/` | `discovery-gate.ts` | Pure completeness check on a spec (requirements have scenarios, etc.) — the discovery gate. |
| gaps | `src/gaps/` | `gaps-store.ts` | CRUD over reconciliation gap records (spec-vs-code drift) in `spec/gaps/`. |
| issues | `src/issues/` | `issues-store.ts` | CRUD over logged issue records in `spec/issues/`. |
| backlog | `src/backlog/` | `backlog-store.ts` | CRUD over prioritized backlog items in `spec/backlog/`. |
| delivery | `src/delivery/` | `tool-adapter.ts` | Renders skills/commands/agents for an AI tool; `claude-code-adapter.ts` targets Claude Code, `workflow-primer.ts` primes the orchestrator. |
| docs | `src/docs/` | `doc-generator.ts` | Generates the user-facing `docs/` (architecture, api, changelog, getting-started) from specs (`DocGenerator`). |
| templates | `src/templates/` | `template-engine.ts` | Resolves + renders artifact templates from a search-path chain; the `src/templates/` subdirs are the source assets copied to `dist/` and deployed. |
| util | `src/util/` | `slug.ts` | Cross-cutting helpers: `slug.ts` (slugify), `errors.ts` (`getErrorMessage`), `duration.ts`, `git-log-timings.ts`. |
| cli | `src/cli/` | `index.ts`, `helpers.ts` | Commander entry point (`index.ts` registers every command) and `createCliContext` (`helpers.ts`) which wires all stores/engines together. |

## Layered architecture

metta follows a strict **functional core, imperative shell** layering. Dependencies
point downward only — the CLI knows about engines, engines know about stores,
stores know about schemas, and nothing points back up.

```
  ┌─────────────────────────────────────────────────────────────┐
  │  CLI  (Commander)              src/cli/index.ts              │
  │  one register*Command() per verb: propose, plan, execute,   │
  │  verify, finalize, ship, issue, backlog, gate, …            │
  └───────────────────────────────┬─────────────────────────────┘
                                  │ createCliContext()
                                  ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  CliContext                    src/cli/helpers.ts            │
  │  single wiring point — constructs & holds every engine/store │
  └───────────────────────────────┬─────────────────────────────┘
                                  │
        ┌──────────────┬──────────┼───────────┬──────────────┐
        ▼              ▼          ▼           ▼              ▼
  ┌───────────┐ ┌───────────┐ ┌────────┐ ┌──────────┐ ┌───────────┐
  │ Workflow  │ │ Execution │ │ Gate   │ │Finalizer │ │  Context  │  core
  │  Engine   │ │  Engine   │ │Registry│ │+SpecMerge│ │  Engine   │  engines
  └─────┬─────┘ └─────┬─────┘ └───┬────┘ └────┬─────┘ └─────┬─────┘
        │             │           │           │             │
        └──────┬──────┴───────────┴─────┬─────┴─────────────┘
               ▼                        ▼
        ┌──────────────────────────────────────────┐
        │  Stores:  ArtifactStore · StateStore ·    │  imperative
        │  SpecLockManager · Gaps/Issues/Backlog ·  │  shell (I/O)
        │  ConfigLoader · TemplateEngine            │
        └──────────────────┬───────────────────────┘
                          ▼
        ┌──────────────────────────────────────────┐
        │  Schemas (Zod)        src/schemas/        │  validation
        │  every read/write is validated here       │
        └──────────────────────────────────────────┘
```

`createCliContext(projectRoot)` in `src/cli/helpers.ts` is the single composition
root: it builds the `ArtifactStore`, `WorkflowEngine`, `ContextEngine`,
`GateRegistry`, `IssuesStore`, `BacklogStore`, `GapsStore`, `SpecLockManager`,
`TemplateEngine`, `InstructionGenerator`, and `StateStore`, then hands them to the
command handlers as a `CliContext`. There are no singletons — each invocation
constructs a fresh context rooted at the project directory.

## The change lifecycle (end to end)

A change flows through six phases. The classes below are the load-bearing code at
each step.

1. **Propose** — `metta propose` creates the change. `ArtifactStore.createChange`
   (`src/artifacts/artifact-store.ts`) slugifies the description, writes
   `ChangeMetadata` (status `active`, first artifact `ready`, the rest `pending`)
   and records `base_versions` for the capabilities it will touch. The
   `WorkflowEngine` (`src/workflow/workflow-engine.ts`) determines which artifacts
   exist and their dependency-ordered `buildOrder`. A change branch is created and
   the proposer/product/researcher subagents author the intent, stories, spec, and
   research artifacts.

2. **Plan / Execute** — `metta plan` and `metta execute` walk the `buildOrder`.
   For each artifact the `ContextEngine` (`src/context/context-engine.ts`) loads
   the manifest's required + optional files within a token budget, the matching
   subagent authors the artifact, gates declared on that artifact run via the
   `GateRegistry` (`src/gates/gate-registry.ts`), and `ArtifactStore` promotes the
   status to `complete` and advances `current_artifact`. Implementation tasks are
   parsed from `tasks.md` (`src/planning/tasks-md-parser.ts`) and run by the
   `ExecutionEngine` (`src/execution/execution-engine.ts`) — sequentially or across
   parallel git worktrees (`WorktreeManager`), batched by `batch-planner.ts`.

3. **Finalize** — `metta finalize` runs `Finalizer.finalize`
   (`src/finalize/finalizer.ts`) under a PID-aware `finalize-lock.ts`. It:
   - derives the workflow-scoped gate set from the workflow YAML,
   - merges the change's delta spec into the capability specs via
     `SpecMerger.merge` (`src/finalize/spec-merger.ts`), which compares each
     requirement's `base_versions` hash against the live `spec.lock`
     (`SpecLockManager`) and reports `clean` or `conflict`,
   - runs the scoped gates,
   - regenerates user docs (`DocGenerator`),
   - and archives the change via `ArtifactStore`.

4. **Ship** — `metta ship` merges the change branch to main through
   `merge-safety.ts` (`src/ship/merge-safety.ts`): it records a snapshot tag,
   re-runs gates, detects conflicts, and emits a stepped `MergeSafetyResult`.
   Merge safety is intentionally defense-in-depth — the design goal is that no path
   silently loses committed work.

Two convenience entry points wrap this: `metta quick` skips the planning artifacts
for small changes, and `metta auto` drives the whole discover→build→verify→ship
loop. In AI-orchestrated sessions these are invoked via the matching `metta-*`
**skill**, never the raw CLI (see [guard-hooks.md](./guard-hooks.md)).

## Functional core, imperative shell

The codebase deliberately separates **pure logic** (deterministic, no I/O, trivially
testable) from the **imperative shell** (filesystem, git, child processes).

**Pure core (no I/O):**
- `SpecMerger.merge` decides `clean` vs `conflict` purely from delta specs and
  version hashes — it touches the `StateStore` only to read inputs and write the
  merged result, the *decision* is pure.
- `WorkflowEngine`'s topological sort + cycle detection
  (`WorkflowCycleError`) is a pure graph operation over parsed YAML.
- `batch-planner.ts` (`planBatches`) and `parallel-wave-computer.ts` compute
  execution batches/waves from task dependencies with zero side effects.
- `discovery-gate.ts` (`checkDiscoveryCompleteness`), `complexity/scorer.ts`, and
  `stories/story-validator.ts` are pure predicates over text/structured input.

**Imperative shell (I/O at the edges):**
- `StateStore` (`src/state/state-store.ts`) is the only place YAML hits the disk;
  it validates against a Zod schema on **both** read and write and manages
  lock files.
- `GateRegistry` spawns shell commands (process groups, timeouts).
- `WorktreeManager` and `merge-safety.ts` shell out to git.
- `ConfigLoader`, the `*Store` classes, and `DocGenerator` read/write files.

When adding logic, keep the decision pure and push the read/write to a store.
A pure function with the I/O injected is the house style — see how `Finalizer`
takes its stores by constructor injection rather than constructing them inline.

## Templates: source → built → deployed

metta ships assets (workflow YAML, gate definitions, artifact templates, skills,
agents, hooks, statusline, docs templates) that must reach the user's project.
There are two distinct paths and one byte-identity invariant.

```
  src/templates/{workflows,gates,gate-scaffolds,artifacts,        (source of truth)
                 skills,agents,docs,hooks,statusline}
        │
        │  npm run build  →  tsc && copy-templates
        ▼
  dist/templates/…                                                (build output)
        │
        │  metta install  (delivery/claude-code-adapter.ts)
        ▼
  <project>/.claude/{agents,skills,hooks,statusline}              (deployed copy)
```

- **`copy-templates`** (a `package.json` script) `cp -r`s each `src/templates/`
  family into `dist/templates/` after `tsc`. Per project convention, template
  files are **copied**, never inlined as string literals in TypeScript.
- **`metta install`** deploys agents/skills/hooks/statusline into the project's
  committed `.claude/` directory via the delivery adapter.

**Why byte-identity matters.** For the families that have a *committed* deployed
copy (`agents`, `skills`, `hooks`, `statusline`), the deployed `.claude/` file must
stay byte-identical to its `src/templates/` source. If they drift, the project
ships a stale agent/skill/hook silently — this actually happened (the deployed
`metta-verifier` agent drifted from its template and went undetected for weeks).
`tests/template-deploy-sync.test.ts` guards against this: it auto-discovers every
file in each source family and asserts byte equality with its deployed copy, so
coverage can never silently regress. Workflows/gates/artifacts/docs are excluded —
they are build-copied to `dist/` and have no separately committed deployed copy,
so they can't drift this way.

## Where to start when changing code

- Adding a CLI verb → `src/cli/commands/` + register it in `src/cli/index.ts`,
  pulling collaborators from `createCliContext`.
- Changing a state shape → start at `src/schemas/` (the validated contract), then
  the owning store.
- Adding a workflow / gate / agent / skill → see [extending.md](./extending.md)
  and remember the template byte-identity rule above.
- Touching merge or finalize → `SpecMerger`, `Finalizer`, `merge-safety.ts`; these
  carry the work-loss-prevention guarantees and deserve extra test coverage.
