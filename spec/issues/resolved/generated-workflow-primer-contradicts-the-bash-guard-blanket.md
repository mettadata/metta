# Generated workflow primer contradicts the bash guard — blanket CLI ban hides the permitted read-only surface

**Captured**: 2026-08-26
**Status**: logged
**Severity**: major

## Symptom
The workflow primer generated by `metta refresh` (injected into every consumer project's CLAUDE.md `metta:workflow` region) states a blanket ban: "AI orchestrators MUST invoke the matching metta skill — never call the CLI directly," and the Forbidden section bans "any other `metta <cmd>` directly from an AI orchestrator session." The actual enforcement hook, `metta-guard-bash.mjs`, explicitly permits a read-only CLI surface. Consumer sessions treat the primer wording as authoritative and never discover the permitted commands — the zeus session (2026-08-26) spent hours grepping `spec/**` and `dist/` instead of running allowed queries, hand-computed a wrong milestone rollup (12 vs the CLI's correct 13), and told its operator that permitted read-only commands were forbidden.

## Root Cause Analysis
The primer text in `src/delivery/workflow-primer.ts` was written when the guard model was simpler and has drifted from the enforcement authority. `metta-guard-bash.mjs` now carries three allow structures — `ALLOWED_SUBCOMMANDS` (status, instructions, progress, doctor, next, iteration, model-escalation, tokens, install), `ALLOWED_TWO_WORD` (issues list, gate list, changes list, backlog list|show, gaps list|show, milestone list|show, release status), and `ALLOWED_BARE` (roadmap, backlog, release with flags) — checked before any block/identity gate, failing closed only on unrecognized commands. The primer's `MANDATE` constant and the Forbidden bullet describe none of this; they claim all direct CLI invocation is forbidden. Because `metta refresh` regenerates the CLAUDE.md region from these strings, the wrong wording is authoritative in every consumer project, and local corrections (zeus commit 919720e) sit inside the generated region and are reverted on the next refresh. The same blanket wording also exists in metta's own CLAUDE.md workflow section and docs/workflows/README.md. There is no shared source of truth between the primer strings and the hook's allow-lists, so they drift independently.

### Evidence
- `src/delivery/workflow-primer.ts:11` — the `MANDATE` constant hardcodes "never call the CLI directly," reused in both the short (line 32) and long (line 47) primer variants that refresh injects.
- `src/delivery/workflow-primer.ts:60` — the Forbidden bullet bans "any other `metta <cmd>` directly from an AI orchestrator session," contradicting the hook's allow surface.
- `.claude/hooks/metta-guard-bash.mjs:38` — `ALLOWED_SUBCOMMANDS` (with `ALLOWED_TWO_WORD` at line 48, `ALLOWED_BARE` at line 96, decision logic at lines 671-674) is the enforcement authority permitting read-only commands the primer claims are forbidden.

## Candidate Solutions
1. **Scope the primer to mutating commands and add a permitted read-only subsection** — Rewrite `MANDATE` and the Forbidden bullet to enumerate the state-mutating commands that require skills, name `metta-guard-bash` as the enforcement authority, and add a "Read-only queries (permitted directly)" subsection carrying the allow-list; apply the same wording to metta's own CLAUDE.md and docs/workflows/README.md (three copies, two strings in workflow-primer.ts). Tradeoff: the primer text and hook allow-lists remain hand-synced, so they can drift again the next time the hook changes.
2. **Generate the read-only list from a shared manifest** — Extract the allow-lists into a shared module or JSON manifest consumed by both `metta-guard-bash.mjs` and `workflow-primer.ts`, so refresh always emits exactly what the hook permits and drift is structurally impossible. Tradeoff: the hook is a standalone .mjs loaded by Claude Code hooks while the primer is built TypeScript — sharing a source requires either the hook importing from dist/ (stale-checkout hazard already logged as an issue) or a build step copying the manifest, adding coupling and build complexity.
3. **Wording fix only in the primer, defer sync mechanism** — Do solution 1's rewrite but keep the read-only subsection generic ("the guard hook permits read-only status/list queries; when in doubt attempt the command — the hook fails closed"), avoiding an enumerated list that can go stale. Tradeoff: consumers still don't get a concrete command list, so discoverability improves only partially and sessions may still under-use the permitted surface.
