# Forked metta skills return early while their background work is still running, leaving orphaned agents and stale locks

**Captured**: 2026-07-14
**Status**: resolved
**Severity**: major

## Symptom
Forked metta skills (context: fork, hosted by metta-skill-host) return control to the orchestrator while background work they launched is still running. Observed twice on 2026-07-13/14 in one session: (1) the /metta-propose fork returned saying "The proposer is authoring intent.md in the background. I'll wait for it to complete" but the fork had already exited — the change record existed with intent.md unwritten, the orchestrator resumed via metta-next, and the fork's orphaned background proposer completed minutes later, racing a duplicate proposer the orchestrator had spawned (the duplicate had to be killed). (2) The /metta-ship fork returned saying "The finalize dry-run is running in the background. I'll wait for it to complete" — no finalize process was running afterwards, and a stale lock file .metta/locks/finalize-<change>.lock remained holding dead pid 2936177; the orchestrator verified the pid was dead, removed the lock by hand, and drove finalize itself.

## Root Cause Analysis
Primary cause: the fork's contract has no synchronous-completion rule. Neither .claude/agents/metta-skill-host.md nor any forked SKILL.md forbids `run_in_background` Bash calls or background Agent dispatch, and nothing requires the fork to block until launched work completes before ending its turn. When the host model launches work in the background and then emits prose like "I'll wait for it to complete", emitting that final message ends the subagent's turn — the subagent terminates and its text is returned to the orchestrator as the result, while its background children are orphaned. The orphaned child either completes later and races orchestrator-driven recovery (propose case) or is torn down without cleanup (ship case).

Secondary cause (the stale lock): `acquireFinalizeLock` registers lock cleanup via `process.once('exit', ...)`, which never fires if the orphaned finalize process is killed hard (SIGKILL / harness teardown), so the lock file survives its owner. Notably, dead-pid reaping at acquisition ALREADY exists (shipped in dcdc467fe, 2026-06-22): a lock whose pid fails `process.kill(pid, 0)` is silently reclaimed on the next `metta finalize`. So a plain retry would have self-healed. The manual cleanup the orchestrator performed was steered by the FinalizeLockError message, which says "remove the stale lock at <path>" — and that error only throws while the pid is alive, meaning the orchestrator likely hit it while the orphan still lived, then found the dead-pid lock afterwards. The remaining real gaps: liveness is only checked inside finalize acquisition (no reaping/reporting from `metta status`/`metta next`), the error message recommends manual deletion instead of retry, and there is no mtime/heartbeat fallback equivalent to state-store's 60s stale-lock rule for pid-recycling or EPERM edge cases.

### Evidence
- `.claude/agents/metta-skill-host.md:21` — the host contract only says "When the skill completes, return a short summary"; there is no rule forbidding background dispatch or requiring the fork to await launched work before ending its turn, so the observed early return violates no stated constraint.
- `src/finalize/finalize-lock.ts:87` — cleanup is registered with `process.once('exit', cleanup)`, which does not run when the orphaned finalize process is killed hard, explaining the surviving lock file owned by dead pid 2936177.
- `src/finalize/finalize-lock.ts:67` — `acquireFinalizeLock` already treats a dead-pid lock as stale and reclaims it (dcdc467fe, 2026-06-22), so the reported "no dead-pid reaping" is partially incorrect; the gap is confined to the error-message guidance, non-finalize surfaces, and the absence of a time-based staleness fallback.

## Candidate Solutions
1. **Synchronous-completion contract for forked skills** — Add a hard rule to `.claude/agents/metta-skill-host.md` and each `context: fork` SKILL.md: the fork MUST NOT use `run_in_background` on Bash, MUST NOT dispatch background agents, and MUST NOT end its turn while any launched tool call or subagent is pending — it either blocks until completion or returns an explicit machine-readable resumable-state block (change slug, artifact, pid) instead of prose claiming to wait. Tradeoff: prompt-level rules are advisory — a model can still violate them, and long-running work (full finalize, multi-batch execution) then occupies the fork's context window for its whole duration.
2. **Mechanical enforcement via hooks** — Extend the metta-guard-bash PreToolUse hook to reject `run_in_background: true` Bash calls when `event.agent_type` starts with `metta-`, and add a Stop/SubagentStop hook that blocks the fork from ending its turn while background tasks it launched are still registered. Tradeoff: more hook machinery to maintain and test; SubagentStop semantics vary across Claude Code versions, and a false-positive block could wedge a fork that has legitimately finished.
3. **Harden the finalize lock lifecycle** — Bring the finalize lock up to state-store parity: reap and report dead-pid locks from `metta status` and `metta next` (not just at finalize acquisition), add an mtime-based 60s staleness fallback for pid-recycling/EPERM cases, and rewrite the FinalizeLockError message to say "re-run finalize — stale locks are reclaimed automatically" instead of recommending manual deletion. Tradeoff: treats the downstream symptom, not the orphaning itself; a wrongly-reaped lock (e.g. a slow but live finalize on the mtime fallback) could allow two concurrent finalizes against the same change.

## Resolution

**Resolved**: 2026-08-08 (stale-issue sweep)

Fixed by fix-forked-metta-skills (2026-07-15): synchronous-completion contract in metta-skill-host.md + guard-bash mechanical block on run_in_background + dispatch-guard hook. Residual Agent-dispatch recurrence tracked by forked-skill-agent-dispatch-orphaning-recurred-after-the.
