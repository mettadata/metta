# Harden metta-guard-bash trust model: unify all blocked subcommands on the unforgeable agent_type signal and retire the forgeable METTA_SKILL=1 bypass

**Captured**: 2026-06-22
**Status**: resolved
**Severity**: major

## Symptom
The metta-guard-bash PreToolUse hook (.claude/hooks/metta-guard-bash.mjs and the byte-identical src/templates/hooks/metta-guard-bash.mjs) splits blocked metta subcommands into two trust tiers. SKILL_ENFORCED_SUBCOMMANDS (propose, quick, auto, ship, issue, fix-issue) require BOTH the inline METTA_SKILL=1 prefix AND a trusted event.agent_type starting with "metta-". Every OTHER blocked subcommand (complete, finalize, refresh, import, init, fix-gap) is gated by METTA_SKILL=1 alone. Because METTA_SKILL=1 is just text in the command string, an AI orchestrator can forge it (e.g. typing `METTA_SKILL=1 metta finalize`) and bypass the guard for the non-enforced tier — the exact privilege-escalation class the archived change fix-metta-guard-bash-allows-ai-orchestrators-bypass-skill closed for the enforced tier but left open here.

## Root Cause Analysis
The offender predicate in main() (metta-guard-bash.mjs:148-156) branches on SKILL_ENFORCED_SUBCOMMANDS. For enforced subcommands it returns `!(inv.skillBypass && isTrustedSkillCaller(event))`; for all others it returns the legacy `!inv.skillBypass`, so the forgeable inline prefix is sufficient. isTrustedSkillCaller (line 105-107) is the only non-forgeable signal: it reads event.agent_type, which the Claude Code runtime populates ONLY when the tool fires from a forked subagent. The fork topology determines whether the enforced model can be applied universally: a skill calling a blocked CLI command inside a forked metta-* subagent has agent_type populated; a skill running in the main orchestrator context does not. Fork-topology audit of .claude/skills/*/SKILL.md frontmatter shows exactly SIX skills declare `context: fork` + `agent: metta-skill-host` (auto, ship, issue, fix-issues, quick, propose) — precisely the enforced set. The non-enforced blocked subcommands are called from a MIX of contexts: `complete`/`finalize` are invoked by forked skills (propose, quick, auto, ship, fix-issues) but ALSO by NON-forked skills (metta-plan, metta-execute, metta-verify, metta-next, metta-fix-gap); `refresh` by non-forked metta-refresh and metta-init; `import` and `init` by non-forked metta-import / metta-init; `fix-gap` by non-forked metta-fix-gap. Those non-forked skills run in the main orchestrator context where agent_type is absent, so naively moving every blocked subcommand to the enforced model would BLOCK legitimate calls (over-block) and lock out plan/execute/verify/next/refresh/import/init/fix-gap. The METTA_SKILL=1 → config-loader warning is a side effect of the same env var: applyEnvOverrides (src/config/config-loader.ts:69-104) strips the METTA_ prefix and maps METTA_SKILL into config key `skill`, which ProjectConfigSchema rejects, emitting the "METTA_* environment variable(s) caused config validation errors (ignored)" warning at config-loader.ts:154 on every skill call that exports the var into the loader process env.

### Evidence
- `.claude/hooks/metta-guard-bash.mjs:148` — offender predicate returns `!inv.skillBypass` for non-enforced subcommands, accepting the forgeable inline prefix as sufficient authorization.
- `.claude/hooks/metta-guard-bash.mjs:105` — isTrustedSkillCaller reads event.agent_type, the only non-forgeable trust signal, populated only inside a forked subagent; non-forked skills lack it.
- `src/config/config-loader.ts:78` — applyEnvOverrides lowercases the post-prefix remainder (METTA_SKILL → `skill`) and injects it as a config key, producing the recurring unrecognized-key validation warning at line 154.

## Candidate Solutions
1. **Per-subcommand fork-context migration (recommended)** — Fork the non-forked skills that call blocked subcommands (metta-plan, metta-execute, metta-verify, metta-next, metta-fix-gap, metta-refresh, metta-import, metta-init) so agent_type is reliably populated, then collapse SKILL_ENFORCED_SUBCOMMANDS to cover ALL blocked subcommands and require isTrustedSkillCaller everywhere; retire METTA_SKILL=1 and the process.env fallback (line 140) and the inline prefix entirely, which also eliminates the config-loader warning. Tradeoff: high blast radius — converting eight skills to context: fork changes their execution model and context budget, and any skill missed during migration is hard-locked out; requires full guard test-suite coverage plus identical edits to both byte-identical hook copies.
2. **Keep METTA_SKILL=1 as a non-trust co-marker, add agent_type as the authority** — Require isTrustedSkillCaller for ALL blocked subcommands but only after first forking the non-forked skills; retain METTA_SKILL=1 purely as an explicit-intent annotation (no longer sufficient on its own) and separately patch ProjectConfigSchema to reserve/ignore the `skill` key so the warning disappears without removing the env var. Tradeoff: leaves a dead forgeable token in the command strings (confusing, invites future regressions where someone re-trusts it) and adds a config-schema special case that must be maintained.
3. **Config-loader-only patch (narrow, does NOT close the bypass)** — Add `skill` to a reserved-name allowlist in config-loader so the warning stops, leaving the two-tier guard model untouched. Tradeoff: cosmetic only — it silences the noise but the major privilege-escalation bypass on complete/finalize/refresh/import/init/fix-gap remains fully open; should be flagged as out-of-scope-alone, not a fix for this issue.

## Resolution

**Resolved**: 2026-08-08 (stale-issue sweep)

Fixed by the two-tier trust model change: Tier-1 via runtime agent_type, Tier-2 via server-minted session credential; METTA_SKILL=1 fully retired (zero references in either hook copy).
