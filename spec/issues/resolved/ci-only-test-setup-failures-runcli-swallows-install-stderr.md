# CI-only test-setup failures: runCli swallows install stderr and metta install dies on 2-core runners, blocking PR #79

**Captured**: 2026-08-11
**Status**: logged
**Severity**: major

## Symptom
The CI gates job failed 3/3 runs on PR #79 (fix-finalize-resolves-specdir-session-cwd) with 4-10 failures per run in `tests/cli-finalize.test.ts` and `tests/cli-complete.test.ts`, all with the same signature: the setup-phase `metta install --git-init` child process dies in about 1 second without creating `.metta/`, so every subsequent state read in the test fails with ENOENT on `.metta/config.yaml`. The identical commit passes the full suite locally (2122/2122, twice, including pinned to 2 CPUs), and main's CI is green. `cli-complete.test.ts` is untouched by the PR; the only plausible interaction is a scheduling shift introduced by two new real-git-worktree e2e tests. CI logs contain no stderr from the dead install process, so the actual failure cause is invisible.

## Root Cause Analysis
Two stacked defects. (1) Diagnosability: `runCli` in `tests/helpers/cli.ts` catches every exec failure and converts it into a `{ stdout, stderr, code }` return value; setup-phase callers (e.g. `await runCli(['install', '--git-init'], tempDir)`) discard that return without asserting `code === 0`, so a failed install is completely silent — the first visible error is a downstream ENOENT that reads like an unrelated flake, and CI logs never show why install died. The helper already adds a stderr marker for timeout kills, but nothing surfaces it when the caller ignores the result. (2) The underlying CI-only startup failure: `vitest.config.ts` sets no worker or file-parallelism caps, so CI runs vitest's default worker-per-CPU parallelism, and every `runCli` call execs an `npx tsx src/cli/index.ts` chain (npx wrapper process → tsx → node) per CLI invocation. The heaviest CLI-fixture files (`cli-finalize`, `cli-complete`) each spawn dozens of these chains; on a resource-constrained GitHub runner, concurrent workers each spawning multi-process chains is consistent with process-spawn resource exhaustion (EAGAIN/ENOMEM at fork time) or npx cache/binstub contention killing the child within ~1s before the CLI writes anything. The PR's two new real-git-worktree e2e tests plausibly shifted file scheduling so the heavy fixture files now run concurrently, crossing the resource threshold — explaining why an untouched test file fails and why local runs (even at 2 CPUs, without CI's memory limits and cold npx cache) pass. Defect (1) must be fixed first regardless: until stderr/exit-code/signal from setup failures is surfaced, the true CI-side errno cannot be confirmed.

### Evidence
- `tests/helpers/cli.ts:48-63` — the catch branch swallows exec failure into a plain return value; nothing throws or logs, so an install that dies at spawn leaves zero trace in CI output.
- `tests/cli-finalize.test.ts:33` — setup calls `await runCli(['install', '--git-init'], tempDir)` and ignores the result (same pattern at 9 sites in this file and 10 in `cli-complete.test.ts`), so a non-zero install exit proceeds straight into ENOENT territory.
- `vitest.config.ts:3-14` — no `maxWorkers`/pool caps and no serialization of heavy CLI-fixture files, so CI concurrency is scheduler-dependent; each worker multiplies the per-call `npx tsx` process chain, the candidate exhaustion mechanism.

## Candidate Solutions
1. **Loud setup helper** — Add an `installFixture(dir)` (or general `runCliOrThrow`) helper to `tests/helpers/cli.ts` that runs the CLI and throws with exit code, signal, and full stderr/stdout when the setup-phase command fails or `.metta/config.yaml` is missing afterwards; migrate all ~19 setup call sites in `cli-finalize.test.ts`/`cli-complete.test.ts` (and other fixture files) to it. This converts the next CI failure into a direct diagnosis of the real errno. Tradeoff: does not fix the underlying failure — at least one more red CI run is needed to capture the evidence, and the failures remain until the root cause is addressed.
2. **Cap CI concurrency** — Pin vitest workers in CI (e.g. `maxWorkers` via env or config, or `fileParallelism: false` for the CLI-fixture files via a sequential project/pool) so the heavy exec-storm files never run concurrently on the runner. Cheap, likely eliminates the exhaustion trigger immediately, and unblocks PR #79. Tradeoff: increases CI wall-clock time and treats the symptom — the suite stays fragile to any future scheduling shift if the cap is ever loosened.
3. **Reduce per-call process cost** — Drop the `npx` wrapper (resolve the local tsx binary path directly) or build the CLI once per CI run and exec `node dist/cli/index.js`, cutting each CLI invocation from a 3-process chain to 1 and removing npx cache contention. Tradeoff: most invasive — running from `dist` diverges from testing the source entry point (stale-dist class of bugs), and the helper's tsx-resolution comment/contract must be reworked across the suite.
