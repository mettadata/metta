# Forked skill Agent-dispatch orphaning recurred after the synchronous-completion contract shipped — turn-level enforcement is needed. On 2026-07-15, with the contract rule live in .claude/agents/metta-skill-host.md (merged in a642ad010), the /metta-fix-issues fork still returned early with "The proposer agent is writing the intent artifact. I'll wait for it to complete before advancing the workflow" — the exact forbidden pattern (final message narrating in-flight work, turn ended with a dispatched Agent pending). The orchestrator recovered via the established wait-for-orphan pattern, but this confirms the prediction recorded in the fix-forked-metta-skills change intent (archived 2026-07-15): contract prose cannot reliably prevent Agent-dispatch orphaning because nothing mechanically stops a fork from ending its turn. The Bash run_in_background case IS mechanically blocked (guard-bash hook, verified live); the Agent-dispatch case has no equivalent. Fix direction (deferred as out-of-scope in that change): a Stop/SubagentStop hook that blocks a metta-skill-host fork from ending its turn while it has pending background children, if/when Claude Code hook semantics support it reliably — or alternatively instruct forks to use synchronous Agent dispatch only (no background flag on the Agent tool from fork context). Interim mitigation for orchestrators is documented in the skill-host rule: treat any fork summary narrating in-progress work as a failed fork and wait for the orphaned agent's completion rather than duplicating its work.

**Captured**: 2026-07-15
**Status**: logged
**Severity**: minor

## Symptom

On 2026-07-15, with the synchronous-completion contract live in `.claude/agents/metta-skill-host.md` (shipped in the fix-forked-metta-skills change, commits 93dd29646 and eb1cc8509), a `/metta-fix-issues` fork again ended its turn with a dispatched Agent still pending, returning the exact forbidden pattern as its final message: "The proposer agent is writing the intent artifact. I'll wait for it to complete before advancing the workflow." The orchestrator recovered via the documented wait-for-orphan pattern, but the fork orphaned its child agent despite the contract rule that forbids exactly this.

## Root Cause Analysis

The synchronous-completion rule is contract prose, not mechanism. Nothing in Claude Code intercepts a subagent ending its turn, so a fork that emits a final message while a dispatched Agent is still running simply returns — the framework hands that text to the orchestrator and the child is orphaned. The prior change made the Bash half of this failure mechanical: `metta-guard-bash.mjs` is a PreToolUse hook on the Bash tool and rejects `run_in_background: true` from any `metta-*` agent_type (verified live). But the Agent-dispatch half has no equivalent: PreToolUse on Bash never sees Agent tool calls, and no Stop/SubagentStop hook exists to block a metta-skill-host fork from ending its turn while it has pending background children. That gap was explicitly deferred as out of scope in the archived change intent, which predicted this exact recurrence ("A follow-up issue may revisit turn-level enforcement if background-Agent dispatch ... turns out to cause the same failure"). This issue is that follow-up: the prediction has now been confirmed in production, so turn-level (or Agent-dispatch-level) enforcement is needed rather than prose.

### Evidence
- `.claude/agents/metta-skill-host.md:24` — the hard rule forbidding ending a turn with a dispatched Agent pending was live at the time of the recurrence, proving prose alone cannot prevent the failure.
- `.claude/hooks/metta-guard-bash.mjs:145` — mechanical enforcement exists only for the Bash `run_in_background` case from `metta-*` callers; there is no hook path covering Agent-tool dispatch or turn-ending.
- `spec/archive/2026-07-15-fix-forked-metta-skills-return-early-while-their-background/intent.md:40` — Agent-dispatch orphaning was explicitly scoped out ("no hook-level enforcement is added for the Agent-dispatch case"), with a follow-up issue anticipated if it recurred.

## Candidate Solutions

1. **Stop/SubagentStop hook with pending-children check** — Add a SubagentStop (or Stop) hook that fires when a `metta-*` fork attempts to end its turn and blocks the stop (exit 2 / decision "block") if the fork has pending background children, forcing the model to keep waiting. Tradeoff: depends on Claude Code hook semantics reliably exposing both the stop event for subagents and a way to enumerate pending child agents from the hook event; the prior change deferred this precisely because those semantics were not yet reliably available across supported versions.

2. **PreToolUse enforcement on the Agent tool from fork context** — Extend the guard-hook approach to the Agent tool: when `event.agent_type` starts with `metta-`, reject any Agent dispatch form that runs in the background, so forks can only use synchronous Agent dispatch (mirroring the existing Bash `run_in_background` block). Tradeoff: only works if the Agent tool's background behavior is distinguishable in the PreToolUse payload; if background execution is implicit rather than flag-driven, the hook cannot tell a synchronous dispatch from one the fork will abandon, and over-blocking would break skills that legitimately spawn personas.

3. **Codify orchestrator-side recovery as the contract** — Accept that prevention is not currently mechanizable and harden the documented interim mitigation: treat any fork summary narrating in-progress work as a failed fork, and have the orchestrator (or `metta next`) detect incomplete artifacts and wait for / attach to the orphaned agent instead of duplicating its work. Tradeoff: this is recovery, not prevention — the duplicate-proposer race window remains, and detection rests on textual heuristics over the fork's summary rather than a mechanical signal.
