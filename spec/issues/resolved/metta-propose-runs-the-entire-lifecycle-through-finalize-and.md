# /metta-propose runs the entire lifecycle through finalize and ship (PR merged to main) with no stop point — reported by the zeus session (2026-08-19, their per-DEX-switch change PR #28): the orchestrator invoked /metta-propose expecting the propose entry point to produce intent/spec (and at most stop at an open PR for review), but the fork ran discovery → planning → implementation → verification → finalize → ship and MERGED the PR autonomously. Same behavior observed in the metta repo itself (the backlog/milestones rework via /metta-propose ran to merged PR #85). Notably the propose-stop-after capability exists in the living specs (71 requirements) — so either (a) the skill ignores the configured/default stop-after behavior, (b) the default stop point is ship which contradicts the capability intent and least surprise for a verb named propose, or (c) stop-after only binds the CLI and was never wired into the fork skill step list. RCA should determine which and fix accordingly: propose should stop at its documented stop-after point by default (likely after planning artifacts or at PR-open-for-review), with running through ship an explicit opt-in (/metta-auto is the documented full-lifecycle verb — propose duplicating it makes the two entry points indistinguishable). Also update skill docs and the CLAUDE.md workflow section to state each entry point stop behavior precisely.

**Captured**: 2026-08-18
**Status**: logged

## Symptom
Invoking `/metta-propose` runs the entire change lifecycle — discovery, planning artifacts, implementation, review, verification, finalize, push, PR creation — and then merges the PR to main autonomously, with no stop point. Reported by the zeus session (2026-08-19, per-DEX-switch change, PR #28) and reproduced in the metta repo itself (backlog/milestones rework via `/metta-propose` ran to merged PR #85). The orchestrator expected propose to produce intent/spec and at most stop at an open PR for review; instead the fork shipped and merged without user consent, despite the `propose-stop-after` capability (71 requirements) existing in the living specs.

## Root Cause Analysis
Of the reporter's three hypotheses — (a) skill ignores stop-after, (b) default stop point is ship, (c) stop-after binds only the CLI — the answer is (b), by deliberate design of both spec and skill. The `propose-stop-after` capability was specified as strictly opt-in: the spec requires that when `--stop-after` is NOT supplied, no `stop_after` field is written at all, "preserving the current YAML output for callers that do not opt in." The stop-after boundary check IS correctly wired into the fork skill (step 3 checks `STOP_AFTER` after every `metta complete` and halts with a handoff line), so (a) and (c) are false. But when the flag is absent, the skill's step 8 unconditionally runs finalize → `git push` → `gh pr create` → `gh pr checks --watch` → `gh pr merge --merge` ("unless the user asked to leave it open for review"), and a dedicated section titled "Critical: You MUST verify, finalize, and ship" explicitly commands "Do NOT stop after the last artifact — finalize + ship must happen." So the default path of a verb named "propose" is a full autonomous ship-and-merge, which (1) violates least surprise, (2) sits in tension with the constitution's "No auto-push to remote without explicit user confirmation," and (3) makes `/metta-propose` behaviorally identical to `/metta-auto`, the documented full-lifecycle verb. The merge-by-default behavior was introduced/retained when PR-based shipping replaced direct local merges (commits 04c58aa1d, 52bc59de2) — the ship flow got safer (CI-gated PR) but the default terminal state stayed "merged," and no default stop point was ever defined for propose.

### Evidence
- `.claude/skills/metta-propose/SKILL.md:281-284` — the "Critical: You MUST verify, finalize, and ship" section commands "Do NOT stop after the last artifact — finalize + ship must happen," making full lifecycle the mandated default when no stop-after is set.
- `.claude/skills/metta-propose/SKILL.md:272-277` — step 8 pushes the branch, opens a PR, watches CI, then runs `gh pr merge <pr-number> --merge` "unless the user asked to leave it open for review" — merge is the default, leaving open is the opt-out.
- `spec/specs/propose-stop-after/spec.md:70` — "When `stopAfter` is not supplied, the constructed `ChangeMetadata` MUST NOT include a `stop_after` field — preserving the current YAML output for callers that do not opt in" — confirming the capability was scoped as opt-in flag handling only, never as a default stop policy for the propose verb (`src/cli/commands/propose.ts:38-39` likewise only acts when the option is present; no config default exists).

## Candidate Solutions
1. **Default stop at PR-open-for-review** — Change skill step 8 and the "Critical" section so the default terminal state is: finalize, push, open PR, report the PR URL, and stop — merging requires explicit opt-in (e.g. `--ship` flag, or the user saying "merge it"), inverting the current "merge unless asked to leave open" clause. `/metta-auto` remains the full-lifecycle verb that merges. Add a spec delta to `propose-stop-after` (or a new capability) codifying each entry point's default stop, and update skill docs + the CLAUDE.md workflow section to state stop behavior per verb. Tradeoff: changes behavior existing users/sessions may rely on, and touches both template (`src/templates/skills/metta-propose/SKILL.md`) and installed skill copies which must stay in sync.
2. **Default `STOP_AFTER=tasks` for propose** — When no `--stop-after` is passed, propose defaults to stopping after planning artifacts (the existing boundary machinery already handles this cleanly, printing the `/metta-execute` handoff line), making "propose" literally mean propose. Tradeoff: a larger behavior shift — users who want propose to also build now need an extra command or flag, and the common propose-then-build flow gains friction; requires the same doc/spec updates as option 1.
3. **Config-driven default stop point** — Add `defaults.stop_after` (per-verb) to metta config, read in `propose.ts` alongside the existing `defaults.workflow` fallback, persisted to the change record so the skill's existing persisted-`stop_after` check (step 3, second boundary condition) enforces it with zero new skill logic. Ship a sane shipped default (PR-open). Tradeoff: the most implementation surface (schema, config-loader, CLI, spec deltas, tests), and without a shipped non-null default it fixes nothing for projects that never set the config key.
