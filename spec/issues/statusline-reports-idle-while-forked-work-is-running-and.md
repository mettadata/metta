# Statusline reports idle while forked work is running and context percent exceeds 100%

**Captured**: 2026-08-11
**Status**: logged
**Severity**: minor

## Symptom
Observed live in the zeus tmux pane on 2026-08-11: the statusline rendered `[metta: idle] 297%` while a fix-issues fork (metta-skill-host subagent) was mid-change. Two independent wrongs compound: the activity segment claims idle while real work is running in a fork/worktree, and the context percent exceeds 100% (297% where ~59% is expected for a 1M-window model), because the denominator is a hardcoded 200k window.

## Root Cause Analysis
Three distinct defects in `.claude/statusline/statusline.mjs` (mirrored byte-for-byte in `src/templates/statusline/statusline.mjs`, so any fix must land in both). (1) `resolveContextWindow` returns 1,000,000 only when the model id contains the literal substring `[1m]`, otherwise a hardcoded 200,000. Current model ids such as `claude-fable-5` carry a 1M window but do not match the substring, so the denominator is 5x too small — 297% instead of ~59%. The window should come from the statusline stdin payload's model/context fields when available instead of substring sniffing, and `computePercent` has no clamp or flag for >100% values. (2) `findLatestAssistantUsage` sums `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` from the last assistant record of the main transcript only; this arithmetic should be re-verified against how the harness reports effective context after compaction. (3) Activity detection shells out to `metta status --json` from the project root and reads a top-level `current_artifact`. That top-level field exists only in the single-change JSON shape; the zero-change and multi-change paths emit `{ changes: [...] }` with no top-level `current_artifact`, and changes hosted in a fork's worktree are invisible to the root artifact store entirely — so the parser silently falls through to `idle` exactly when work is running in a fork or worktree. The desired behavior is for the statusline to reflect fork/background-agent activity for the session being viewed (e.g. a hook-maintained activity file under `.metta/scratch/` written on Agent dispatch/SubagentStop, or parsing aggregated worktree change data from root `metta status`).

### Evidence
- `.claude/statusline/statusline.mjs:8` — `resolveContextWindow` sniffs for the `[1m]` substring and otherwise hardcodes 200,000, so a 1M-window model id like `claude-fable-5` gets a 5x-too-small denominator, and `computePercent` (line 49) never clamps the result.
- `.claude/statusline/statusline.mjs:92` — the activity block only accepts a top-level `current_artifact` string from `metta status --json` and defaults to `idle` on any other shape or on command failure, hiding fork/worktree activity.
- `src/cli/commands/status.ts:29` — the zero-change path emits `{ changes: [], message }` and the multi-change path (line 65) emits `{ changes: [...] }`, neither carrying the top-level `current_artifact` the statusline parser expects; worktree-hosted changes never appear in the root `listChanges()` at all.

## Candidate Solutions
1. **Resolve the window from the stdin payload with a clamped fallback** — Read the context-window size from the statusline stdin JSON's model/context fields when the harness provides them, fall back to a small model-id lookup table (not substring sniffing) otherwise, and clamp the rendered percent at 100% with an explicit overflow marker (e.g. `>100%!`) so a bad denominator is visible instead of absurd. Tradeoff: the statusline stdin schema varies across Claude Code versions and may not expose window size, so the fallback table must be verified against docs and will drift as new models ship.
2. **Hook-maintained activity file for fork awareness** — Have hooks write a session-scoped activity file under `.metta/scratch/` on Agent dispatch and SubagentStop (and/or skill-session mint), and have the statusline prefer that file over `metta status --json`, while also teaching the parser to understand the aggregated `{ changes: [...] }` shape. Tradeoff: introduces a new piece of hook-maintained mutable state that can go stale if a hook fails or a session dies, showing phantom activity until a TTL or cleanup pass clears it.
3. **Extend `metta status --json` with a stable top-level summary** — Add an aggregated top-level field (e.g. `active: { change, current_artifact, workflow }`) that the CLI computes across root and worktree-hosted changes so the statusline parses one stable shape regardless of change count or location. Tradeoff: changes the CLI JSON contract (schema validation, other consumers, docs) — a heavier, spec-touching change than a statusline-local fix, and it still cannot see fork activity that has not yet written any change state.
