# Backlog feature duplicates data instead of referencing existing logged issues — observed live in zeus (2026-08-16): spec/backlog/ items created via metta backlog add are standalone files (title + description re-entered), completely disconnected from spec/issues/, so backlogging an already-logged issue copies its content into a second file with no link — two sources of truth that drift (issue gets RCA updates, backlog copy goes stale; resolving one leaves the other dangling). Desired design (user direction): the backlog should NOT mint parallel content for issues — an issue enters the backlog by marking up the EXISTING issue file itself, e.g. frontmatter on the issue markdown (backlog: true / priority / ordering or a status field), with backlog list/promote/done reading and mutating that frontmatter; standalone backlog items would remain only for non-issue ideas (or be unified entirely under one store). Affects src/backlog/backlog-store.ts, src/cli/commands/backlog.ts (add/promote/done), the metta-backlog skill, and the issue-store read path; migration consideration for existing spec/backlog/ items in consumer projects (zeus has live data in both stores).

**Captured**: 2026-08-15
**Status**: logged
**Severity**: major

## Symptom
Observed live in zeus (2026-08-16): backlogging an already-logged issue via `metta backlog add` creates a standalone file under `spec/backlog/` with the title and description re-entered by hand, completely disconnected from the original `spec/issues/` file. The result is two sources of truth that drift — the issue file receives RCA updates while the backlog copy goes stale, and resolving one leaves the other dangling.

## Root Cause Analysis
`BacklogStore` and `IssuesStore` are structurally parallel but fully disconnected stores. `BacklogStore.add()` always mints a brand-new markdown file from a caller-supplied title and description; its `BacklogItem` shape has no field capable of referencing an issue slug, and no code path in either store reads across to the other. The CLI's `backlog add` command simply forwards `title`/`--description` text into that mint path, and the `metta-backlog` skill's add flow re-asks the user for title and description free-form — so when the "item" is an existing issue, its content is retyped/copied rather than referenced. The `--source` option looks like a linking mechanism but is freeform display metadata (e.g. `idea/dark-mode`): nothing validates it against `spec/issues/`, and nothing on the `promote`/`done` paths consults it, so even a conscientious user cannot create a real link today. Desired design (user direction): an issue should enter the backlog by marking up the existing issue file itself — e.g. frontmatter on the issue markdown (`backlog: true`, priority/ordering, or a status field) — with `backlog list/promote/done` reading and mutating that frontmatter; standalone backlog items would remain only for non-issue ideas, or the two stores would be unified entirely. Migration must account for consumer projects (zeus) with live data in both `spec/backlog/` and `spec/issues/`.

### Evidence
- `src/backlog/backlog-store.ts:59` — `add()` constructs a fresh `BacklogItem` from raw title/description and writes a new `spec/backlog/<slug>.md`; the `BacklogItem` interface (lines 6-13) has no issue-reference field, only a freeform optional `source` string.
- `src/cli/commands/backlog.ts:60` — the `add` action passes `options.description ?? title` straight to `backlogStore.add()`, and `promote` (line 94) / `done` (line 135) operate purely on `spec/backlog/` files — no code path ever touches `spec/issues/`.
- `src/issues/issues-store.ts:8` — the `Issue` shape carries only `status: 'logged'` and severity metadata parsed from bold-label lines, with no frontmatter and no backlog/priority fields, so the issue read path cannot currently represent backlog membership.

## Candidate Solutions
1. **Issue-frontmatter backlog membership (user-directed design)** — Add frontmatter (or extend the bold-label metadata block) on issue files: `backlog: true`, optional `priority`, optional ordering. Teach `backlog list` to merge frontmatter-flagged issues with standalone `spec/backlog/` items, `backlog add <issue-slug>` to flip the flag on an existing issue instead of minting a file, and `promote`/`done` to mutate the issue's frontmatter/status. Standalone backlog files remain only for non-issue ideas. Tradeoff: two read paths in `backlog list` (issues + standalone items) adds parsing complexity, and issue files gain a second metadata format (frontmatter vs bold labels) unless the issue store is migrated wholesale.
2. **Reference-only backlog entries** — Keep `spec/backlog/` as the single backlog store, but when the source is an issue, write a thin pointer file (`ref: issues/<slug>`) with no copied content; `show`/`promote` dereference to the issue file at read time, and `done` archives both sides. Tradeoff: still two files per backlogged issue (pointer + issue), dangling-pointer handling needed when an issue is resolved or removed out-of-band, and consumers must migrate existing duplicated items into pointers.
3. **Unify the stores** — Collapse `BacklogStore` and `IssuesStore` into one item store where "backlogged" and "logged" are statuses/flags on a single file, with a migration command that merges existing `spec/backlog/` and `spec/issues/` entries (deduplicating zeus's live duplicates by slug/title match). Tradeoff: largest blast radius — touches `src/cli/helpers.ts` wiring, `fix-issue`, `metta-backlog`/`metta-issue`/`metta-fix-issues` skills, specs for both capabilities, and requires a careful data migration for every consumer project.
