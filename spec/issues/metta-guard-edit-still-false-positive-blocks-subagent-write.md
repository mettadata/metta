# metta-guard-edit still false-positive blocks subagent Write/Edit inside .metta/worktrees/<change>/ in a consumer project despite the PR #57 worktree-aware fix

**Captured**: 2026-08-17
**Status**: logged
**Severity**: major

## Symptom
Reported live by the zeus consumer session (2026-08-18): subagents editing files under zeus's `.metta/worktrees/<change>/` checkouts are still blocked by metta-guard-edit ("no active metta change") and fall back to bash heredocs — the exact symptom the 2026-08-08 fix-metta-guard-edit-worktree-blind change (PR #57) was supposed to end. Zeus runs freshly installed hooks (reinstalled 2026-08-16 post-PR#85 and 2026-08-18 post-PR#86), so this is not a stale hook copy. Meanwhile `metta status` from the session cwd (the main checkout) resolves the change fine, matching zeus's "resolves change from session cwd, not the target file" observation — inverted: the change IS visible from the session cwd but NOT from the target's checkout.

## Root Cause Analysis
Reproduced in a consumer-shaped fixture against the current installed hook and the globally-linked dist (2026-08-18). The hook's only fail-closed path is a probe that SUCCEEDS with the empty envelope `{"changes":[],"message":"No active changes"}`: every probe failure (metta missing from PATH, non-zero exit, schema-validation error exit 4, timeout) is caught and fails open (verified by direct execution — `env PATH=/usr/bin:/bin` and an invalid `.metta.yaml` both exit 0). This disproves the "probe error treated as no-active-change" candidate. The canonical PR #57 topology (change state inside the worktree's own `spec/changes/`) also allows correctly, for absolute targets, not-yet-existing deep paths, and relative paths alike. What blocks — reproduced exactly, hook exit 2 — is an inverted-hosting topology: the change's `spec/changes/<name>/.metta.yaml` lives in the MAIN checkout while the edit target lives in `.metta/worktrees/<change>/`. The hook resolves the target's git toplevel (the worktree), runs `metta status --json` there, and `resolveProjectRoot` stops at the worktree's `.git` without ever consulting the parent checkout — so a worktree checkout that does not carry the change state (state never committed to the change branch and the worktree re-created/pruned-and-re-added, or the change created by a flow/version that wrote state at the main root while still using a worktree) reports "No active changes", and the hook treats that successful-but-wrong-root answer as authoritative and hard-blocks. Discovery is one-directional by design: the main root aggregates `<root>/.metta/worktrees/*/spec/changes/`, but a worktree-rooted store never looks back at the main checkout. The guard-edit test suite substitutes a shim `metta` binary, so this real-CLI asymmetry is uncovered by tests. Fail-open-vs-fail-closed decision needed: a successful empty envelope from a NON-session root should be treated as inconclusive (probe the session cwd root before blocking) rather than authoritative.

### Evidence
- `.claude/hooks/metta-guard-edit.mjs:94-116` — the probe runs `metta status --json` only at the target's checkout root and hard-blocks on a successful empty envelope; there is no session-cwd fallback, while every probe *failure* is caught at lines 105-107 and fails open (verified: PATH without metta and invalid `.metta.yaml` both exit 0; main-hosted change + worktree target exits 2).
- `src/cli/helpers.ts:58-64` and `src/artifacts/artifact-store.ts:208-220` — `resolveProjectRoot` stops the walk at the worktree's `.git`, and change discovery only aggregates worktree-hosted changes from the main root, never main-hosted changes from a worktree root, so `metta status` at a state-less worktree checkout returns `{"changes":[]}` even when the parent checkout hosts the active change (reproduced in fixture).
- `tests/metta-guard-edit.test.ts:252-264` — the worktree-awareness suite injects a shim `metta` that answers by cwd, so the real CLI's one-directional discovery and the inverted-hosting topology are never exercised; all shim tests pass while the consumer topology blocks.

## Candidate Solutions
1. **Two-root probe with either-allows semantics** — after a successful empty envelope from the target's checkout root, re-probe with cwd set to the hook's session root (`process.cwd()`), and allow if either root reports an active change; keep hard-block only when both agree there is none. This directly encodes the fail-open decision for the inconclusive case and fixes the reproduced topology without touching the CLI. Tradeoff: adds a second `metta status` subprocess on the would-block path (latency) and slightly weakens the guard — any active change in the main checkout now authorizes edits in every worktree, including unrelated ones.
2. **Bidirectional CLI discovery** — teach `resolveProjectRoot`/`ArtifactStore` that a worktree checkout whose own `spec/changes` is empty should resolve the parent main checkout (via the worktree `.git` file's gitdir pointer or `git worktree list`) and aggregate its changes, so `metta status` inside a worktree reports main-hosted changes symmetrically; the hook is fixed for free, as are `metta instructions`/`tokens record` invoked from worktree cwds. Tradeoff: broadens status semantics across checkouts for every CLI consumer, reintroduces slug-collision ambiguity in the opposite direction, and touches core resolution used by all commands.
3. **Keep state hosting canonical instead** — make the lifecycle guarantee the worktree always carries its change state (commit `spec/changes/<name>/` to the change branch at propose/quick time, and have worktree re-creation repair missing state from the main copy), so the inverted topology can no longer arise and the hook stays as-is. Tradeoff: does not protect existing in-flight consumer changes already in the inverted state, and adds commit side-effects to propose/quick that the stop-after contract must account for; any future flow that forgets the guarantee regresses silently because the guard-edit tests still shim the CLI.
