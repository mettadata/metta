# fix-forked-skill-agent-dispatch-orphaning-recurred-after

## Problem

A forked `metta-*` skill (hosted by `metta-skill-host`, `context: fork`) can dispatch an `Agent` call and end its own turn before that agent returns. When that happens the framework returns the fork's final text — however it phrases the situation — to the orchestrator as the fork's *completed* result, and the dispatched child agent keeps running unsupervised. This is the Agent-dispatch counterpart of the Bash `run_in_background` orphaning fixed in the archived change `fix-forked-metta-skills-return-early-while-their-background` (commits 93dd29646, eb1cc8509): that change added a hard contract rule to `.claude/agents/metta-skill-host.md` ("You MUST NOT dispatch an `Agent` call and end your turn before that agent returns") and a mechanical `metta-guard-bash.mjs` PreToolUse block for the Bash half, but explicitly deferred the Agent-dispatch half as out of scope, predicting it would recur.

It recurred the same day the contract rule shipped. On 2026-07-15 a `/metta-fix-issues` fork ended its turn with the message "The proposer agent is writing the intent artifact. I'll wait for it to complete before advancing the workflow." — the exact forbidden pattern the new rule named — while its dispatched proposer agent was still running. The orchestrator recovered by hand via the documented wait-for-orphan pattern. Per the user's additional context, this failure mode has now been observed on effectively every forked-skill invocation across the v0.2 milestone (`/metta-propose`, `/metta-quick`, `/metta-ship`, `/metta-fix-issues` — 8+ occurrences), each requiring manual orchestrator recovery, and one early occurrence produced a duplicate-proposer race that required killing an agent by hand.

Root cause: the synchronous-completion rule is contract prose, not a mechanism. Nothing in Claude Code intercepts a subagent ending its turn while it has a pending dispatched `Agent` child — `metta-guard-bash.mjs` is a PreToolUse hook scoped to the `Bash` tool and never sees `Agent` tool calls, and no `Stop`/`SubagentStop` hook exists today to check for pending children before letting a `metta-*` fork stop. A rule the model can silently violate under load is not enforcement.

Affected parties: every AI orchestrator session driving metta through its primary supported entry points — the six `context: fork` skills (`metta-issue`, `metta-fix-issues`, `metta-propose`, `metta-quick`, `metta-auto`, `metta-ship`). Each recurrence costs a manual recovery cycle (pid inspection, waiting for or re-attaching to the orphaned agent) and, in the worst observed case, a duplicate-work race that had to be killed by hand.

## Proposal

Per Claude Code's documented hook semantics (code.claude.com/docs/en/hooks, verified 2026-07-17): `SubagentStop` fires when a subagent attempts to end its turn and can block the stop via exit code 2 or `{"decision":"block","reason":"..."}`, feeding `reason` back to the agent so it continues its turn instead of returning. `Stop` hooks declared in subagent frontmatter are automatically converted to `SubagentStop` for that subagent. Neither event exposes pending-background-children state directly in its payload, so the hook must track that itself. This change ships a layered fix, in preference order, landing as many layers as the runtime supports and always landing the floor layer:

1. **Primary — turn-end blocking via a pending-dispatch ledger.** Add a `SubagentStop` hook (new file, template+deployed pair per this project's hook-editing discipline) scoped to `metta-*` `agent_type` callers. The hook consults a per-fork dispatch ledger — written by a companion `PreToolUse`/`PostToolUse` pair on the `Agent` tool that records "child dispatched" on `PreToolUse` and "child returned" on `PostToolUse` for that `agent_id` — and blocks the stop (`decision: "block"`) with a reason telling the model to wait for the outstanding child, whenever the ledger shows an undispatched-return delta at stop time. This is landed only if research/design confirms `PreToolUse`/`PostToolUse` reliably fire for `Agent` tool dispatches with an `agent_id` correlatable across the pre/post pair and into the `SubagentStop` payload — this must be verified empirically before implementation, per the unresolved fact in the research notes (fact d: the `Agent` tool_input schema and whether a background-style flag or correlatable id is exposed is undocumented).
2. **Secondary — `PreToolUse` policing of `Agent` dispatch shape.** If the runtime does not support (1) as designed, extend `metta-guard-bash.mjs`'s sibling pattern to a new `PreToolUse` matcher on the `Agent` tool: when `event.agent_type` starts with `metta-`, reject any `Agent` dispatch form that carries a background/non-blocking flag (if the tool schema exposes one), mirroring the existing `run_in_background` rejection for Bash. This is a narrower net than (1) — it prevents an explicitly-async dispatch shape but cannot detect a fork that dispatches a normally-synchronous `Agent` call and then ends its turn anyway before the result returns, since `PreToolUse` cannot see the future `SubagentStop`.
3. **Floor — codified wait-for-orphan recovery protocol (always lands).** Whether or not (1) or (2) land, harden the interim manual mitigation into the contract itself: add a slimmed "if you detect an orphaned fork" recovery section to `.claude/agents/metta-skill-host.md` and to each of the six fork skills (`metta-issue`, `metta-fix-issues`, `metta-propose`, `metta-quick`, `metta-auto`, `metta-ship`), instructing the orchestrator to (a) treat any fork summary that narrates in-progress/background work as a failed, non-terminal fork result rather than success, (b) check for and wait on/attach to the still-running orphaned agent instead of re-dispatching a duplicate, and (c) only re-dispatch fresh work once the orphan is confirmed dead or complete. This directly prevents recurrence of the duplicate-proposer race documented in the prior change and observed again in this issue's history.

The `orchestration-guard` capability spec (`spec/specs/orchestration-guard/spec.md`) is the delta target for any new guard-adjacent MUST/SHOULD requirements introduced by layers 1 and 2; layer 3's contract-only changes are captured as requirements against the same capability where they describe orchestrator-visible behavior (detecting and recovering from a failed fork).

All hook edits follow the established discipline already used for `metta-guard-bash.mjs`: the template under `src/templates/hooks/` and the deployed copy under `.claude/hooks/` MUST be byte-identical, and `node --check` MUST be run immediately after every hook file edit. The six fork skills' existing frontmatter (`context: fork`, `agent: metta-skill-host`) is preserved unchanged — only skill *body* prose gains the recovery section.

## Impact

- `.claude/agents/metta-skill-host.md` — new recovery-protocol prose (layer 3, always); if layer 1 or 2 lands, an additional note cross-referencing the mechanical enforcement now in place.
- New hook file(s) under `src/templates/hooks/` (template) and `.claude/hooks/` (deployed) implementing the `SubagentStop`-based pending-dispatch check (layer 1) and/or the `Agent`-tool `PreToolUse` policing (layer 2), plus any `PreToolUse`/`PostToolUse` ledger-writer companion hook layer 1 requires. `.claude/settings.local.json` (or equivalent hook registration) gains new hook entries for whichever layers land.
- `.claude/hooks/metta-guard-bash.mjs` — unchanged; the existing `run_in_background` Bash block and `SKILL_ENFORCED_SUBCOMMANDS`/Tier-1/Tier-2 classification logic are untouched by this change.
- Each of the six `context: fork` skill bodies under `.claude/skills/` (`metta-issue`, `metta-fix-issues`, `metta-propose`, `metta-quick`, `metta-auto`, `metta-ship`) — audited and given the slimmed recovery-protocol section from layer 3; frontmatter unchanged.
- `spec/specs/orchestration-guard/spec.md` — new/updated MUST/SHOULD requirements covering turn-end pending-child enforcement (if layer 1 or 2 lands) and orphan-recovery behavior (layer 3).
- Orchestrator sessions driving any forked skill gain a stronger completion guarantee than the prior change delivered: either the fork mechanically cannot end its turn with a pending `Agent` child (layers 1/2), or, failing that, the orchestrator has a codified, non-manual protocol for detecting and safely recovering from an orphaned fork without racing a duplicate dispatch (layer 3).
- No change to `src/finalize/finalize-lock.ts` or the finalize lock staleness logic shipped in the prior change — that remains a separate, already-resolved concern.

## Out of Scope

- Changes to non-fork (host-invoked-directly) skills or their contracts — this change is scoped to the six `context: fork` skills and `metta-skill-host.md`.
- CLI or TypeScript `src/` changes outside `src/templates/hooks/`, unless a gate (test, typecheck, or spec-conformance) requires a source-level change to support the new hook(s) — no such change is planned up front.
- A general-purpose `Stop`/`SubagentStop` hook that governs *any* subagent regardless of `agent_type` — scope is limited to `metta-*` fork callers, consistent with the existing `metta-guard-bash.mjs` trust model.
- Re-litigating or modifying the Bash `run_in_background` enforcement already shipped in `metta-guard-bash.mjs` — that mechanism is confirmed working and is left as-is.
- Finalize-lock lifecycle, `metta-guard-edit.mjs`, or `SKILL_ENFORCED_SUBCOMMANDS`/Tier-1/Tier-2 classification logic — none of these are touched by this change.
- Retroactively detecting or cleaning up any currently-orphaned agents or stale artifacts left over from past occurrences of this bug; this change fixes the mechanism going forward only.
- Building a general async/background task supervisor for metta skills beyond the specific fork-turn-ending failure mode described here.
