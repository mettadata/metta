# Implementation: make-metta-guard-bash-tokenizer-quote-aware-stop-false

Resolves issue `metta-guard-bash-hook-false-positive-quoted-free-text`.

## The bug

`tokenize()` in the metta-guard-bash PreToolUse hook splits the entire command
string on whitespace. After matching a `metta <sub>` invocation it advanced with
`i += 3; continue`, re-scanning for another `metta` token starting at `i+3`
instead of skipping past the current command's argument list. As a result, words
inside a quoted argument (for example a propose description that itself mentions
`metta finalize`) were misparsed as a phantom second invocation and wrongly
blocked (the hook exited 2).

## The fix

In `tokenize()`, the `metta`-match branch now skips the remainder of the current
command's arguments up to the next chain separator (`&&`, `;`, `||`, `|`) — the
same separator set already used elsewhere in the function — before continuing the
scan. This mirrors the existing "skip until separator" logic used for non-`metta`
leading tokens, so quoted free-text arguments can no longer produce a phantom
invocation, while genuine chained `metta` commands are still detected.

Before:

```js
    if (tokens[i] === 'metta') {
      results.push({ sub: tokens[i + 1], third: tokens[i + 2], skillBypass });
      i += 3;
      continue;
    }
```

After:

```js
    if (tokens[i] === 'metta') {
      results.push({ sub: tokens[i + 1], third: tokens[i + 2], skillBypass });
      // Skip the rest of this command's arguments up to the next chain separator
      // so words inside a quoted argument (e.g. a propose description that mentions
      // "metta finalize") are not misparsed as a second invocation.
      i += 1;
      while (i < tokens.length && !['&&', ';', '||', '|'].includes(tokens[i])) i++;
      i++; // skip the separator
      continue;
    }
```

The patch was applied identically to both copies of the hook, which must remain
byte-identical:

- `.claude/hooks/metta-guard-bash.mjs`
- `src/templates/hooks/metta-guard-bash.mjs`

### Byte-identical confirmation

`diff .claude/hooks/metta-guard-bash.mjs src/templates/hooks/metta-guard-bash.mjs`
reported no differences both before the edit (baseline) and after the edit. The
test suite's own `'source and deployed hook are byte-identical'` assertion also
passes.

## Regression test

Added to `tests/metta-guard-bash.test.ts` (inside the per-hook `describe`, so each
case runs against both the source template and the deployed mirror):

1. `metta status "see metta finalize docs"` — the quoted argument text contains
   `metta finalize`. Expectation: NOT blocked, exit 0. Before the fix this exited
   2 because the tokenizer re-scanned the free-text words and matched a phantom
   `metta finalize` invocation.
2. `metta status && metta finalize` — a genuine chained command. Expectation:
   STILL blocked, exit 2. This proves the skip-to-separator change does not break
   detection of real chained metta commands.

```ts
// ----- Quote-aware tokenization: free-text args must not trigger phantom invocations -----
it('allows `metta status "see metta finalize docs"`: quoted arg text is not a phantom invocation (exit 0)', () => {
  const { code } = runHook(hookPath, bashEvent('metta status "see metta finalize docs"'))
  expect(code).toBe(0)
})

it('still blocks a genuine chained `metta status && metta finalize` (exit 2)', () => {
  const { code } = runHook(hookPath, bashEvent('metta status && metta finalize'))
  expect(code).toBe(2)
})
```

The pre-existing chain-detection coverage (`cd /foo && metta issue "bar"`,
`METTA_SKILL=1 metta status && metta propose "foo"`) also still passes, confirming
real chained metta commands remain caught.
