# consolidate-ai-orchestration-layer-single-source-truth-v0-2

## Problem

The AI-orchestration layer that decides which persona each subagent receives, which workflow YAML a tier resolves to, and which gate scaffolds exist for non-JS stacks has drifted into multiple, disagreeing sources of truth. This is v0.2 step 5a of the 2026-07 framework review, and it surfaces four concrete divergences:

1. **Persona duplication.** Agent personas are authored once in `.claude/agents/metta-*.md` (11 files, deployed via `src/templates/agents/`), but `src/cli/commands/instructions.ts` (lines 7-17) re-declares 9 of them as a hardcoded `BUILTIN_AGENTS` record with its own persona strings, capabilities, tools, and context budgets. Skill files may also re-embed persona text inline. When the agent-file persona changes, `instructions.ts` and skill files do not — so the text a subagent actually receives at `metta instructions` time can silently diverge from the canonical `.claude/agents/` definition that a human (or Claude Code natively) would read. There is also a silent fallback (`BUILTIN_AGENTS[agentName] ?? BUILTIN_AGENTS.executor`, line 50) that maps any unrecognized agent name to the executor persona without any signal that a mapping failed. Engineers maintaining personas and users relying on subagents receiving the correct instructions are both affected.

2. **Phantom specifier.** The `standard` and `full` workflow YAMLs assign the spec artifact to `agents: [specifier]`, but no `metta-specifier.md` agent file exists anywhere in the repo. `instructions.ts`'s `BUILTIN_AGENTS` silently aliases `specifier` to the proposer's capabilities/tools under a differently-worded persona string ("requirements engineer focused on completeness and testability"), meaning the workflow's stated intent (a distinct requirements-engineering persona for delta-spec authoring) is never actually honored by anything backed by a real agent file. This is a second flavor of the same silent-substitution problem as (1), but rooted in a missing artifact rather than a stale copy.

3. **Trivial/quick workflow duplication.** `trivial.yaml` and `quick.yaml` in `src/templates/workflows/` are functionally identical — same three artifacts, same gates — differing only in name and description. The complexity tier scorer maps the `trivial` (≤1 file) and `quick` (2-3 files) tiers to these workflow names respectively, so both names must keep resolving to a workflow, but maintaining two byte-for-byte-equivalent YAML files (other than name/description) is duplicated surface area that must be kept in sync by hand on every future workflow-shape change, with no mechanism (the `extends` YAML-aliasing feature was removed in step 4a) currently enforcing that sync.

4. **Gate-scaffold liveness is unverified.** The 2026-07 review flagged the 12 go/python/rust gate-scaffold YAMLs under `src/templates/gate-scaffolds/` as dead code, reasoning that every real gate hardcodes npm. However `install.ts` (~lines 148-151, 175-190) performs multi-stack detection (`Cargo.toml`, `go.mod`, `pyproject.toml`) and appears to scaffold per-stack gates for consumer projects on non-JS stacks — which would make the scaffolds live and the "dead code" call incorrect. Nobody has verified which claim is true, so any decision to delete or to leave-as-npm-hardcoded is currently a guess rather than a researched conclusion, risking either deleting reachable code (breaking non-JS installs) or leaving genuinely dead code and a documented-but-unfixed npm-hardcoding bug unaddressed.

## Proposal

Consolidate each of the four areas onto a single, verifiable source of truth, with research gating any destructive step:

1. **Personas**: Make `src/templates/agents/` (and its deployed mirror `.claude/agents/`) the single source of truth for persona text. `instructions.ts` MUST derive the `AgentDefinition` it emits (persona, and any other fields sourced from the template) by parsing the agent template file's frontmatter/body at runtime, following the same pattern already shipped for constitution-check instructions in step 4b — not from the hardcoded `BUILTIN_AGENTS` strings. Delete the hardcoded persona/capability/tool/context-budget literals from `instructions.ts` once the runtime-parse path replaces them. Audit skill files for inline persona strings that duplicate or diverge from the agent template files and remove or repoint them to the canonical source.

2. **Phantom specifier**: Research whichever of the two resolutions is less invasive, then implement it: either (a) create a real `metta-specifier.md` agent file (in both `src/templates/agents/` and `.claude/agents/`, byte-identical) carrying the distinct "requirements engineer focused on completeness and testability" persona, keeping the workflow YAMLs' `agents: [specifier]` reference intact and now backed by a real file, or (b) repoint the workflow YAMLs to name `proposer` explicitly wherever spec authoring is assigned, removing the `specifier` alias entirely. Either way, the current silent alias-to-proposer-under-a-different-persona-string behavior in `instructions.ts` MUST be eliminated.

3. **Trivial/quick dedupe**: Research and apply the cheapest honest way to stop maintaining two functionally identical workflow YAMLs by hand, subject to the hard constraint that both the `trivial` and `quick` tier names must keep resolving to a loadable workflow (e.g., have the tier scorer or workflow-loading code map the `trivial` tier name to the `quick.yaml` file and delete `trivial.yaml`, or explicitly document why two near-identical files are being kept as the accepted cost of preserving two distinct tier names). Whichever option is chosen, the decision and its rationale must be recorded, not left implicit.

4. **Gate scaffolds**: Before any deletion, verify via `install.ts`'s multi-stack detection logic (and any integration/e2e coverage of non-JS installs) whether the go/python/rust gate-scaffold YAMLs in `src/templates/gate-scaffolds/` are actually reachable for consumer projects. If they are live, keep them and instead fix whatever npm-hardcoding inconsistency exists in the real gates that the 2026-07 review was reacting to. If research confirms they are genuinely unreachable dead code, delete them.

Cross-cutting constraints for all four areas: no change to what content subagents actually receive at `metta instructions` time unless the change specifically fixes one of the documented divergences above; `src/templates/agents/` and `.claude/agents/` (and any other template/deployed pairs touched) MUST remain byte-identical after each change; the full test suite MUST be green after each implementation batch before moving to the next.

## Impact

- `src/cli/commands/instructions.ts`: the `BUILTIN_AGENTS` hardcoded record and its silent-fallback-to-executor behavior are replaced by a runtime template-parsing code path; any caller depending on the exact current field values must be re-verified against the newly-parsed values.
- `src/templates/agents/` / `.claude/agents/`: a new `metta-specifier.md` may be added (if that branch of proposal item 2 is chosen), and existing agent template files become the enforced source of truth that skill files and `instructions.ts` must not diverge from.
- Skill files (`.claude/skills/*` or equivalent) that currently re-embed persona strings inline are edited to remove or repoint diverging copies; this does not include the 11x-copied agent-types disclaimer, which is explicitly out of scope (see below).
- `src/templates/workflows/` and `.metta/workflows/` (deployed copy) for `trivial.yaml`/`quick.yaml`: either one file is deleted with the tier scorer's mapping updated, or both are kept with the duplication decision documented; any code path that resolves a workflow by filename off the tier name (the complexity/tier scorer) is affected if `trivial.yaml` is removed.
- `src/templates/gate-scaffolds/` (go/python/rust subdirectories) and `install.ts`'s multi-stack scaffolding logic: either left untouched with an npm-hardcoding fix applied elsewhere, or deleted along with any `install.ts` code path that reads them, contingent on the research finding.
- Any existing tests asserting on `BUILTIN_AGENTS` contents, the `specifier` alias behavior, the trivial/quick workflow file layout, or gate-scaffold presence will need to be updated to match the new source of truth.

## Out of Scope

- Guard-bash trust-model unification — tracked as a separate change (v0.2 step 5b), which interacts with the open fork-orphaning Stop-hook issue and is not part of this change.
- The 11x-copied agent-types disclaimer duplicated across skill files — each skill file must remain self-contained per existing convention; this change does not touch or consolidate that disclaimer text.
- CLAUDE.md workflow-section redesign — not addressed by this change.
- Any persona, workflow, or gate-scaffold *content* changes beyond what is needed to fix the four documented divergences (i.e., this is a consolidation/dedup change, not a rewrite of persona wording, workflow artifact/gate composition, or gate-scaffold contents).
