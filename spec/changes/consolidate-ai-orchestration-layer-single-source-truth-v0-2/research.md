# Research: consolidate-ai-orchestration-layer-single-source-truth-v0-2

## 1. instructions.ts anatomy

`src/cli/commands/instructions.ts:7-17` declares `BUILTIN_AGENTS`, a hardcoded `Record<string, AgentDefinition>` with 9 keys (proposer, specifier, product, researcher, architect, planner, executor, verifier, reviewer) — each carrying its own `persona`, `capabilities`, `tools`, `context_budget` string/array literals. Resolution: `instructions.ts:49-50` picks `artifact.agents[0] ?? 'executor'` then does `BUILTIN_AGENTS[agentName] ?? BUILTIN_AGENTS.executor` — an unconditional, silent fallback to the executor persona for any unrecognized name, with no error or log. The resolved `AgentDefinition` is passed as `params.agent` into `InstructionGenerator.generate()` (`src/context/instruction-generator.ts:50-123`), which does **no** agent resolution of its own — it only consumes `params.agent.{name,persona,tools,context_budget,rules}` to build the `InstructionOutput.agent` object (`instruction-generator.ts:109-114`) and to size the context budget (`instruction-generator.ts:62-67`). So `instructions.ts` alone owns agent resolution; `instruction-generator.ts` is a pure consumer.

A **second**, independent hardcoded map exists at `instructions.ts:122-127` (`agentTypeMap`) translating the tier's agent name to a Claude Code `subagent_type` string (e.g. `researcher → 'metta-researcher'`), with `specifier` aliased to `'metta-proposer'` (`instructions.ts:123`) and an `?? 'metta-executor'` fallback (`instructions.ts:128`) — a third silent-fallback path, separate from the `BUILTIN_AGENTS` one.

**Tools divergence, with evidence:** the `tools` array in `BUILTIN_AGENTS` does not match the `tools:` frontmatter in the corresponding `.claude/agents/metta-*.md` file for 6 of 8 agents, e.g. proposer: `['Read','Grep','Glob']` (`instructions.ts:8`) vs. frontmatter `[Read, Write, Grep, Glob, Bash]` (`.claude/agents/metta-proposer.md:5`); researcher: `['Read','Grep','Glob','Bash']` (`instructions.ts:11`) vs. `[Read, Write, Grep, Glob, Bash, WebSearch, WebFetch]` (`.claude/agents/metta-researcher.md:5`). This directly violates the spec's "Emitted Instructions Contract Carries Complete Agent Identity" requirement today.

Note: `reviewer` (`instructions.ts:16`) has no corresponding `agents: [reviewer]` entry in any workflow YAML — review is fanned out ad hoc from skill bodies (§6), not via `metta instructions`, so this key is currently dead in the `BUILTIN_AGENTS` map.

## 2. Agent template file parseability

All 11 files in `src/templates/agents/` (byte-identical to `.claude/agents/`, verified via `diff -rq`, exit 0) use YAML frontmatter (`name`, `description`, optional `model`, `tools: [..]`, `color`) followed by a Markdown body. For the 8 persona-bearing agents (excludes `metta-constitution-checker.md`, `metta-discovery.md`, `metta-skill-host.md`, which are not in `BUILTIN_AGENTS`), the body's **first paragraph**, immediately after the frontmatter and before the first `##` heading, is consistently a single "You are a **role**, focused on X." sentence — e.g. `metta-researcher.md:9`, `metta-verifier.md:8`, `metta-architect.md` first line. This is nearly verbatim what `BUILTIN_AGENTS` already hardcodes as `persona` (markdown-bold vs. plain text is the only difference), so no new authoring is needed — only relocation of the source of truth.

`metta-verifier.md` is 63 lines; its body after the persona paragraph contains operational instructions (verification-context handling, missing-strategy branches, a `## Rules` list) that must **not** be flattened into the `persona` string — `InstructionOutput.agent.persona` is a single display string (`instruction-generator.ts:14-18`), and the existing `.metta/gates`/subagent spawn already gives the real subagent the full file natively (per Claude Code docs, confirmed below). Emitting the whole body as `persona` would balloon the contract and duplicate content Claude Code already loads when it spawns `subagent_type: "metta-verifier"`.

**Parse approach:** reuse the two patterns already shipped in-repo rather than adding a YAML-frontmatter library. (a) `src/delivery/command-installer.ts:30` already extracts a frontmatter field with a per-line regex (`content.match(/^name:\s*(.+)$/m)`) — the same technique extracts `tools:` as a single-line array literal. (b) `src/constitution/constitution-parser.ts:56-96` (the step-4b pattern spec.md cites) already parses a markdown body with `remark-parse` and walks the `mdast` tree by heading boundaries — the same technique, applied here, collects all body nodes before the first heading and renders their text as the `persona` string. Combining both: regex-extract `tools`/`name` from the frontmatter block, remark-extract the pre-heading paragraph as `persona`. This avoids introducing a YAML-frontmatter dependency (`gray-matter` etc. is not present in `package.json`) and stays consistent with existing conventions.

**Proposed convention:** no new `persona:` frontmatter key. Define the rule as "persona = the markdown content between the closing `---` and the first heading" — this is already true for all 8 files with zero edits required, is trivially enforceable (a check can assert the paragraph exists and is non-empty), and avoids a second, hand-maintained copy of the same sentence living inside the frontmatter block (which would reintroduce exactly the drift risk this change is fixing, just one file closer together).

## 3. Specifier decision

`specifier` appears in `standard.yaml:27` and `full.yaml:27` (`agents: [specifier]`), in `instructions.ts:9` (BUILTIN_AGENTS entry) and `instructions.ts:123` (alias to `metta-proposer`) — no `metta-specifier.md` exists in `src/templates/agents/` or `.claude/agents/` (confirmed via `find`). Per Claude Code's subagent docs, `.claude/agents/*.md` files are auto-discovered by walking up from cwd, with frontmatter (`name`, `description`, `tools`, `model`, `color`) and the body as the system prompt — Claude Code "detects the change within a few seconds and the next delegation uses the updated definition, with no restart needed."[^1] So adding a well-formed `metta-specifier.md` pair is sufficient for Claude Code to register it as a real subagent type — no additional registration code is needed (confirmed by the existing `metta-skill-host.md`, which has no bespoke registration logic beyond being copied by `installCommands` at `command-installer.ts:40-55`).

Cost of **(a) create `metta-specifier.md`**: two new byte-identical files (~20 lines, following the `metta-proposer.md` shape) using the persona text that already exists verbatim in `instructions.ts:9` ("You are a requirements engineer focused on completeness and testability."); update `instructions.ts:123` to map `specifier → 'metta-specifier'` instead of `'metta-proposer'`. Cost of **(b) repoint YAMLs to `proposer`**: edit two YAML lines (`standard.yaml:27`, `full.yaml:27`) and delete the `specifier` key/alias entirely.

## 4. Trivial/quick dedupe

`diff src/templates/workflows/trivial.yaml src/templates/workflows/quick.yaml` shows only `name`/`description` differ (lines 1-2); artifacts, `agents:`, and `gates:` are identical. `WorkflowEngine.loadWorkflow(name, searchPaths)` (`workflow-engine.ts:27-61`) resolves the file as `join(searchPath, \`${name}.yaml\`)` (`workflow-engine.ts:38`) — a direct name→filename mapping with no alias layer today, cached per `name` in `this.workflows` (`workflow-engine.ts:25,31,59`, keyed by the input string, not `definition.name`). `metadata.workflow` (the tier name) is what gets passed as `name` everywhere `loadWorkflow` is called (`instructions.ts:45`, `next.ts:90`, `complete.ts:115`, `propose.ts:37`). 50 archived changes reference `workflow: trivial` (2) or `workflow: quick` (43 quick + rest); these are read only via `ChangeMetadataSchema`-validated string comparison in `ceremony-metrics.ts:78` (`metadata.workflow === 'quick' || metadata.workflow === 'trivial'`) — never through `loadWorkflow` — so archived history is unaffected by deleting `trivial.yaml`.

## 5. Gate scaffolds liveness — LIVE, verified by fixture

`install.ts:147-151` detects `Cargo.toml`/`go.mod`/`pyproject.toml`/`package.json`; `install.ts:297-298` calls `scaffoldGateYamls(root, primary, stacks)` when the primary stack is non-JS, which copies `tests.yaml`, `lint.yaml`, `typecheck.yaml`, `build.yaml` from `templates/gate-scaffolds/${primary}/` into `<root>/.metta/gates/` (`install.ts:166-193`), never overwriting existing files (`install.ts:186`). I built (`npm run build`, which runs `copy-templates` and confirmed `dist/templates/gate-scaffolds` is populated) and ran `node dist/cli/index.js install --git-init` in a fresh fixture directory containing only `Cargo.toml`. Result: `Detected stack: rust`, `Scaffolded: 4 gate YAMLs in .metta/gates/`, and the written files contain `cargo build`, `cargo clippy`, `cargo test`, `cargo check` — **correct, non-npm commands**. Verdict: **live, reachable, and correctly stack-specific**, contradicting the 2026-07 review's "dead code" call on two counts (reachability and content).

The real npm-hardcoding inconsistency is downstream of scaffolding, not in the scaffolds: `finalize.ts:38-40` loads `src/templates/gates/` (npm-hardcoded: `npm run build`, `npm run lint`, `npm test`, `npx tsc --noEmit` — `templates/gates/{build,lint,tests,typecheck}.yaml`) **then** loads `.metta/gates/` project-local overrides second, so scaffolded rust/go/python gates correctly override the npm defaults for `finalize`. But `verify.ts:23-24`, `gate.ts:16-17,36-37,55-56` (all three `gate` subcommands), and `ship.ts:34-35` load **only** the npm builtin directory — never `.metta/gates/` — so `metta verify`, `metta gate run/list/show`, and `metta ship` always run `npm test`/`npm run lint`/`npx tsc --noEmit`/`npm run build` even on a Rust/Go/Python project with correctly scaffolded gates sitting unused in `.metta/gates/`.

## 6. Divergent inline personas in skills

`.claude/skills/*/SKILL.md` and `src/templates/skills/*/SKILL.md` are byte-identical (`diff -rq`, exit 0). Every skill's own `You are the **orchestrator** for ...` line (e.g. `metta-verify/SKILL.md:9`) is the orchestrator's *own* session persona — not a copy of any `metta-*` agent file, and out of scope (there is no "metta-orchestrator" agent file to diverge from). Two real divergences found: `metta-verify/SKILL.md:15` — `Persona: "You are a verification engineer focused on spec compliance."` — is a verbatim (minus bold) duplicate of `metta-verifier.md:8`'s persona sentence, hardcoded inline instead of referencing the canonical file. `metta-propose/SKILL.md:209-211` and `metta-quick/SKILL.md:106,138-140` hardcode three narrowed sub-personas for parallel `metta-reviewer` fan-out spawns ("correctness reviewer", "security reviewer", "quality reviewer") that diverge from `metta-reviewer.md`'s single canonical persona ("senior code reviewer focused on quality, security, and correctness") — an intentional narrowing, not an accidental copy, but still an inline persona string outside the agent-file source of truth.

[^1]: https://code.claude.com/docs/en/sub-agents accessed 2026-07-16

## Decision:

1. **Parse approach + persona convention**: parse agent files at runtime using two patterns already shipped in the repo — regex-based single-line frontmatter field extraction (as in `command-installer.ts:30`) for `name`/`tools`, and `remark-parse` AST walking (as in `constitution-parser.ts`) to extract the markdown content between the closing `---` and the first heading as `persona`. No new dependency, no new `persona:` frontmatter key.
2. **Specifier**: create a real `metta-specifier.md` (both copies), reusing the existing persona text already present in `instructions.ts:9`, and repoint the `agentTypeMap` alias at `instructions.ts:123` to `'metta-specifier'`.
3. **Trivial/quick**: delete `trivial.yaml`, add a small filename-alias table (`{ trivial: 'quick' }`) inside `WorkflowEngine.loadWorkflow`'s file-resolution step, keyed by the `name` argument, before the `join(searchPath, ...)` call.
4. **Gate scaffolds**: keep them (verified live). Fix the npm-hardcoding inconsistency by making `verify.ts`, `gate.ts`, and `ship.ts` load `.metta/gates/` after the npm builtin directory, matching the pattern already used in `finalize.ts:38-40`.

### Approaches Considered

- **Personas**: (A) runtime regex+remark parse of existing files [chosen] vs. (B) add a `gray-matter`/YAML-frontmatter dependency and a `persona:` frontmatter key. (B) adds a new dependency and a second hand-maintained copy of the same sentence (frontmatter key + body paragraph), which reintroduces the exact class of drift this change fixes; (A) has zero new dependencies and requires zero edits to the 8 existing agent files, since their bodies already open with a clean, single persona paragraph.
- **Specifier**: (A) create `metta-specifier.md` [chosen] vs. (B) repoint `standard.yaml`/`full.yaml` to `proposer` and delete the alias. (B) is fewer lines changed, but silently drops the workflow authors' stated intent (a distinct requirements-engineering persona) that the review flagged as unhonored rather than fixing it; (A) is confirmed low-cost (Claude Code auto-discovers `.claude/agents/*.md`, no registration code needed) and the persona text to use already exists verbatim in the codebase.
- **Trivial/quick**: (A) delete `trivial.yaml` + alias in `loadWorkflow` [chosen] vs. (B) keep both files with the duplication documented as accepted cost. (B) leaves the exact hand-sync burden intent.md flags, with no enforcement (the `extends` YAML feature was removed in step 4a); (A) is a single, well-contained locus of change, verified safe against archived history (§4) and against the workflow-name cache (keyed by input `name`, not `definition.name`).
- **Gate scaffolds**: (A) keep + fix `verify`/`gate`/`ship` to load `.metta/gates/` [chosen] vs. (B) delete scaffolds as dead code. (B) is factually wrong — fixture-verified live and correctly stack-specific (§5) — and would break non-JS `finalize` parity and any future non-JS `verify`/`gate`/`ship` usage; (A) fixes the actual, evidenced inconsistency (3 of 4 gate-consuming commands ignore `.metta/gates/`) using the exact pattern `finalize.ts` already proves out.

### Rationale

Every decision follows the same principle the change is named for: point every consumer at the one file that already carries the correct, current content, rather than adding a second hand-synced copy (frontmatter persona key, phantom specifier repoint, kept-duplicate workflow, or a scaffold deletion that contradicts the fixture evidence). Each chosen approach was the one with a working precedent already in the codebase (`constitution-parser.ts`, `command-installer.ts`, `finalize.ts`'s two-pass gate loading) or a documented external guarantee (Claude Code's agent-file auto-discovery), minimizing new code and new failure surface while directly resolving the divergence named in intent.md.
