# write-comprehensive-user-contributor-documentation-guide

## Problem

metta has a strong machine-facing documentation substrate but no connective
"explain it to a human" layer. A codebase review identified two audiences with
unmet needs:

**Users** (developers adopting metta on their own projects) have no curated
on-ramp. The spec store under `spec/` is authoritative but is organized for the
framework's own change lifecycle, not for someone learning the tool. The four
generated docs at the root of `docs/` (`api.md`, `architecture.md`,
`changelog.md`, `getting-started.md`) each carry a
`<!-- Generated by Metta — do not edit directly -->` header and are produced by
`metta docs generate` from spec sources. They are reference outputs, not
tutorials or conceptual introductions, and must not be hand-edited.

**Contributors** have no internals guide. The reference set under
`docs/workflows/` (`agents.md`, `artifacts.md`, `gates.md`, `skills.md`,
`state.md`, `walkthroughs.md`, `workflows.md`, `README.md`) is good for
workflow surface coverage but does not explain the subsystem architecture, the
Zod schema / state data model, or how to extend the framework with new
commands, gates, providers, or skills.

Three additional stale or misleading artifacts compound the gap:

- `QA-TEST-GUIDE.md` (repo root) states "185 tests" across "22 files". The
  live suite as of this writing is **1015 tests across 78 test files** (confirmed
  by `npx vitest run`). These numbers misrepresent the project's current state
  to anyone reading the guide.
- `docs/proposed/` holds design documents `00`–`11` plus a `README.md` that
  predate the built system and may have drifted from the implementation. Nothing
  warns a reader that they are historical artifacts.
- There is no `CONTRIBUTING.md` at the repo root and no `docs/README.md` index
  directing each audience to the right starting point.

## Proposal

Add a human-facing documentation layer. Every document MUST be grounded in the
actual code and specs; no invented commands, flags, or behavior.

### docs/guide/ — user-facing docs (new directory)

**`docs/guide/concepts.md`** — mental model and glossary.

Covers the full lifecycle (`propose` → `plan` → `execute` → `verify` →
`finalize` → `ship`) as an ordered sequence. Defines terms used throughout the
CLI and skills: change, spec, artifact, gate, workflow, skill, persona, worktree
branch, and the distinction between QUICK and standard workflows. Notes that
`metta` manages state and specs while the AI tool executes the work.

**Given** a new user has never run metta before,
**When** they read `docs/guide/concepts.md`,
**Then** they understand what a "change" is, why it lives in a git branch
(`metta/<slug>`), and what the sequence propose → plan → execute → verify →
finalize → ship means in concrete terms.

**`docs/guide/getting-started.md`** — a worked-example tutorial.

Walks a reader through a real end-to-end change: `metta install`, then
`metta propose "add a --dry-run flag to metta cleanup"`, through each lifecycle
step, to `metta ship`. Includes expected terminal output at each stage. This
file is distinct from the generated `docs/getting-started.md` and MUST NOT
duplicate its content verbatim.

**Given** a reader follows `docs/guide/getting-started.md` step-by-step in a
project that already has `node >= 22` and `npm install` completed,
**When** they reach the `metta ship` step,
**Then** every `metta` invocation in the tutorial exits zero and their terminal
matches the expected output shown in the guide.

**`docs/guide/cli-reference.md`** — command reference grouped by purpose.

Covers the ~42 registered commands (drawn from `src/cli/commands/` and
`src/cli/index.ts`), organized into groups: setup (`install`, `init`, `update`,
`doctor`, `completion`), lifecycle (`propose`, `quick`, `plan`, `execute`,
`verify`, `finalize`, `ship`, `auto`, `complete`, `next`, `iteration`),
introspection (`status`, `progress`, `changes`, `tasks`, `context`, `gate`,
`specs`, `gaps`, `instructions`), spec management (`import`, `fix-gap`,
`reconcile`, `check-constitution`, `validate-stories`, `refresh`, `docs`),
issue / backlog (`issue`, `issues`, `fix-issue`, `backlog`), and config
(`config get`, `config set`, `config edit`). Each entry includes the command
signature, a one-line description (derived from `program.description()` in the
source), and at least one example invocation.

**Given** a user wants to know what flags `metta propose` accepts,
**When** they look up `propose` in `docs/guide/cli-reference.md`,
**Then** they see the `--workflow`, `--stop-after`, `--discovery`, `--auto`,
`--from-gap`, `--from-idea`, and `--from-issue` options with example values
derived from the actual `registerProposeCommand` source.

**`docs/guide/configuration.md`** — `.metta/config.yaml` documented section
by section.

Covers every top-level key validated by `ProjectConfigSchema` in
`src/schemas/project-config.ts`: `project` (name, description, stack/stacks,
conventions), `defaults` (workflow, mode), `providers` (provider, model,
api_key_env), `tools`, `gates` (command, timeout, required, on_failure), `git`
(enabled, commit_convention, protected_branches, merge_strategy,
snapshot_retention, create_pr, pr_base), `docs` (output, generate_on, types),
`auto` (max_cycles, ship_on_success), `context_sections`, `adapters`, `cleanup`
(log_retention_days), and `verification` (strategy, instructions). Documents
that `METTA_` environment variables override config keys, and notes the
reserved `METTA_SKILL` variable (not a config override).

**Given** a user wants to switch the verification strategy,
**When** they read `docs/guide/configuration.md`,
**Then** they learn the `verification.strategy` key accepts `tmux_tui`,
`playwright`, `cli_exit_codes`, or `tests_only`, and that `metta config set
verification.strategy tests_only` is the command to persist the change.

**`docs/guide/troubleshooting.md`** — common failure modes and recovery steps.

Includes at minimum: config parse errors (`ConfigParseError` with `metta
doctor --fix` remedy), worktree branch conflicts, gate failures (pass/skip/fail
with `on_failure` semantics), stale `METTA_SKILL` environment variable causing
guard rejections, `metta ship` merge conflicts, and `metta docs generate`
producing stale output (re-run triggers).

**Given** a user's `.metta/config.yaml` contains invalid YAML,
**When** they consult `docs/guide/troubleshooting.md`,
**Then** they find the exact error message pattern, the `metta doctor --fix`
recovery command, and an explanation of why `install`, `init`, `doctor`,
`update`, and `completion` are exempt from the preflight config check.

### docs/internals/ — contributor-facing docs (new directory)

**`docs/internals/architecture.md`** — subsystem map and data flow.

Documents the major modules under `src/`: `cli/` (Commander.js entrypoint and
command registration), `config/` (loader, writer, repair), `schemas/`
(Zod schemas for all state and config), `state/` (state-store), `artifacts/`
(artifact-store), `workflow/` (workflow-engine), `gates/` (gate-registry),
`context/` (context-engine), `execution/` (execution-engine), `finalize/`,
`ship/`, `planning/`, `providers/`, `specs/`, `stories/`, `issues/`, `backlog/`,
`gaps/`, `complexity/`, `delivery/`, `constitution/`, `discovery/`, `templates/`,
and `util/`. Shows the data flow for the standard lifecycle: propose creates
state in `.metta/` and `spec/changes/<slug>/`, plan/execute/verify operate
against that state, finalize merges specs into `spec/specs/`, ship merges the
branch to main. This file is explicitly DISTINCT from the generated
`docs/architecture.md` — it is hand-authored and covers implementation
internals, not capability specs.

**Given** a new contributor wants to trace how `metta propose` creates a
change,
**When** they read `docs/internals/architecture.md`,
**Then** they can follow the call graph from `registerProposeCommand` →
`ArtifactStore.createChange` → state written to `.metta/` and `spec/changes/`
without consulting the source code directly.

**`docs/internals/data-model.md`** — schemas, persistence layout, and state
lifecycle.

Documents every Zod schema in `src/schemas/`: `ChangeMetadataSchema`,
`ExecutionStateSchema`, `AutoStateSchema`, `FinalizeLockSchema`,
`SpecLockSchema`, `StateFileSchema`, `WorkflowDefinitionSchema`,
`GateDefinitionSchema`, `GateResultSchema`, `AgentDefinitionSchema`,
`ViolationSchema`, `StorySchema`, `PluginManifestSchema`, and
`ProjectConfigSchema`. Explains the `.metta/` directory layout (state files,
lock files, per-change YAML) and the `spec/` directory layout (`spec/changes/`,
`spec/specs/`, `spec/archive/`, `spec/issues/`, `spec/backlog/`, `spec/gaps/`).
Documents state transitions through the change lifecycle.

**Given** a contributor wants to add a new field to change metadata,
**When** they read `docs/internals/data-model.md`,
**Then** they know which schema to extend, which state-store methods to update,
and what validation constraints apply.

**`docs/internals/extending.md`** — how to add a command, gate, workflow,
skill, or provider.

Covers the four extension points with concrete steps: (1) adding a CLI command
(create `src/cli/commands/<name>.ts` with a `registerXCommand(program)` export,
import and call it in `src/cli/index.ts`, add a corresponding test file); (2)
adding a gate (create a YAML gate definition in `src/templates/gates/`, register
via `GateRegistry`); (3) adding a workflow (create a YAML workflow definition in
`src/templates/workflows/`, reference artifact ids defined in existing schemas);
(4) adding a skill (create a Markdown skill file in `src/templates/skills/`
deployed to `.claude/commands/`); (5) adding a provider (extend the
`providers/` module and update `ProviderConfigSchema`). Notes that template
files are copied to `dist/` at build time via the build process and MUST NOT be
inlined as string literals.

**Given** a contributor wants to add a new `metta summarize` command,
**When** they follow `docs/internals/extending.md`,
**Then** they know to create `src/cli/commands/summarize.ts` with
`registerSummarizeCommand`, add a corresponding test in
`tests/cli-summarize.test.ts`, import and register it in `src/cli/index.ts`,
and build with `tsc` before testing.

**`docs/internals/guard-hooks.md`** — the skill-enforcement policy.

Explains the `metta-guard-bash` and `metta-guard-edit` hook mechanism: the
hooks are installed into the Claude Code tool hooks configuration by `metta
install`, they intercept CLI invocations from AI orchestrators, and they enforce
that AI sessions MUST invoke matching skills (e.g. `/metta-propose`) rather than
calling `metta propose` directly. Documents the `METTA_SKILL` environment
variable used by skills to signal a permitted bypass. Cross-references
`docs/workflows/skills.md` for the canonical skill definitions and the
`spec/issues/` directory for the issue that motivated this guard
(`metta-complete-accepts-stub-placeholder-artifacts-on-intent-`).

**Given** an AI orchestrator calls `metta propose` directly (bypassing the
skill),
**When** the `metta-guard-bash` hook runs,
**Then** the invocation is rejected with an error explaining that the matching
skill must be used, and the orchestrator never creates a change without the
correct artifact-authoring persona.

### Meta and cleanup

**`docs/README.md`** — top-level index for the `docs/` tree.

Maps each audience to its entry point: users start at `docs/guide/`, contributors
start at `docs/internals/`, generated reference docs are `docs/api.md`,
`docs/architecture.md`, `docs/changelog.md`, `docs/getting-started.md` (do not
hand-edit), workflow reference is `docs/workflows/`, historical design sketches
are `docs/proposed/`.

**Given** any reader lands in the `docs/` directory,
**When** they open `docs/README.md`,
**Then** they can identify in under 30 seconds which subdirectory or file serves
their role (user, contributor, or automated tooling).

**Root `CONTRIBUTING.md`** — new file (none exists today).

Covers: prerequisites (Node.js >= 22, `npm install`), building (`tsc`), running
tests (`npm test` / `npx vitest run`), commit convention (conventional commits:
`feat:`, `fix:`, `chore:`, `refactor:`, `test:`, `docs:`), the test-to-source
ratio target (~1:1), the ESM-only constraint (no CommonJS), the no-singletons /
no-unvalidated-state-writes rules, and a pointer to `docs/internals/` for
deeper contributor onboarding.

**Given** an external contributor clones the repo,
**When** they read `CONTRIBUTING.md`,
**Then** they can set up the project, run the full test suite, and understand
the commit format required for a pull request — all without opening any other
file.

**Refresh `QA-TEST-GUIDE.md`** — correct stale counts.

The file currently states "185 tests" across "22 files". The live test suite
is **1015 tests across 78 test files** (confirmed via `npx vitest run` as of
this writing). The count references MUST be updated. Any other stale references
in the file (commands that no longer exist, prerequisite steps that changed)
MUST also be corrected.

**Given** a developer reads `QA-TEST-GUIDE.md` and then runs `npm test`,
**When** the suite completes,
**Then** the test and file counts reported by vitest match the numbers stated
in the guide (within the normal variance of ongoing development).

**Add drift warning to `docs/proposed/`** — header note on older design docs.

The `docs/proposed/` directory holds documents `00-quickstart-usage.md`
through `11-brownfield.md` plus a `README.md`. These were written before the
system was built and may have drifted from the implementation. Each document
(or the `README.md` at minimum) MUST receive a clearly visible header note
such as: "Historical design document — written before v0.1 was built. Content
may have drifted from the current implementation. Treat as background context,
not current reference."

**Given** a reader opens any file under `docs/proposed/`,
**When** they see the header note,
**Then** they are immediately aware that the document is historical background,
not authoritative current documentation.

**Keep `docs/workflows/` canonical** — link, do not duplicate.

The existing `docs/workflows/` reference set (`agents.md`, `artifacts.md`,
`gates.md`, `skills.md`, `state.md`, `walkthroughs.md`, `workflows.md`,
`README.md`) is good. The new docs MUST link to these files rather than
duplicating their content.

## Impact

- New files only under `docs/guide/`, `docs/internals/`, and the repo root
  (`CONTRIBUTING.md`, `docs/README.md`). No source code changes.
- No behavior changes. No new commands, flags, schemas, or tests.
- The four generated docs (`docs/api.md`, `docs/architecture.md`,
  `docs/changelog.md`, `docs/getting-started.md`) are not touched and continue
  to be produced by `metta docs generate`.
- `docs/workflows/` remains the canonical reference set for the workflow
  surface and is linked from the new docs, not duplicated.
- `QA-TEST-GUIDE.md` receives targeted numeric corrections and any other stale
  references fixed; its overall structure and purpose are preserved.
- `docs/proposed/` receives a header warning on its `README.md` (and
  optionally per-file); the documents themselves are not edited for content.

## Out of Scope

- `LICENSE` and `SECURITY` files — a separate project-hygiene workstream.
- Auto-generating the CLI reference via the doc-generator (`metta docs
  generate`) — a possible follow-up; this change authors it by hand.
- Restructuring or regenerating the four generated docs.
- Any changes to `src/`, `tests/`, `spec/specs/`, or `.metta/`.
- Interactive docs tooling (e.g. a website or search index).
