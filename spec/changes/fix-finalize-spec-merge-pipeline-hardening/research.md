# Research: fix-finalize-spec-merge-pipeline-hardening

## Decision:

Use the `<!-- new-capability -->` HTML-comment marker under the delta H1 as the explicit-targeting mechanism (spec.md's own design), but detect it in `complete.ts` via a raw-content regex rather than through `parseDeltaSpec`, because remark drops HTML nodes from the parsed structure. Pre-fill the instructions template's H1 with the literal change name unchanged (existing behavior is fine as a title) but stop treating it as an implicit merge-target default; add a separate `existing_specs` listing (already loaded by `ContextEngine`) to the rendered instructions so authors pick from it. Add the artifact-completeness check as `Finalizer.finalize()`'s new step 1 (before the existing merge call), since it needs zero I/O beyond metadata already loaded. Reorder finalize to dry-run merge → gates → real write → archive, refactoring `SpecMerger.merge`'s internal per-delta `dryRun` branching into a single top-level dry-run pass followed by a conditional write pass, since `mergeSpecs`/`merge` already threads a `dryRun` flag through every write site — no new capability needed, just a second invocation or a write-deferral flag. Make the ADDED branch check `sections.has(name)` via the existing `splitRequirements()` helper and no-op (excluded from `merged`) on match, judged by requirement **name only** (not content hash), consistent with how MODIFIED/RENAMED/REMOVED already key off name.

### Approaches Considered

**1. Capability targeting mechanism** — (a) `<!-- new-capability -->` marker under H1 [spec.md's chosen design]; (b) a `capability:` frontmatter field; (c) an interactive instructions-flow prompt only, no artifact-level marker.
- (a) is what `spec/changes/.../spec.md` (the delta spec for *this* change) already specifies as the requirement text (finalize-ship spec.md:5, 18-20), is parseable as plain text without touching the Zod-validated artifact schema, and needs no new frontmatter block in a markdown-only artifact format (project convention has no frontmatter elsewhere in `src/templates/artifacts/*.md`).
- (b) would require extending `parseDeltaSpec`'s `ParsedDeltaSpec` shape and touching every caller (`src/finalize/spec-merger.ts:44`, `src/cli/commands/complete.ts:161`) plus inventing frontmatter parsing that doesn't exist today (`src/specs/spec-parser.ts` is remark/AST-only, no frontmatter plugin).
- (c) is not durably recorded in the artifact — a bypassed or resumed session would leak the same landfill bug attempt #1 already exhibited.
Confirmed: `src/specs/spec-parser.ts:191` (`parseDeltaSpec`) iterates `tree.children` and only special-cases `heading` and `list` node types; an HTML comment renders as a `type: 'html'` node from `remark-parse` and falls through untouched — it is never captured into `title`, `deltas`, or any field. **The marker is invisible to `parseDeltaSpec` today.** `complete.ts:157-175`'s gate must therefore regex the raw delta content (already reads it via `readFile` at line 160) for the marker rather than relying on the parsed structure, unless the parser is extended — regexing raw content is the lower-blast-radius choice since `SpecMerger.merge` (spec-merger.ts:44) also calls `parseDeltaSpec` and does not need marker awareness (its capability name comes from the caller-confirmed target per finalize-ship spec.md:42, not from re-deriving the H1).
Pre-fill decision: `src/context/instruction-generator.ts:70` sets `capability_name: params.changeName` unconditionally — this is exactly the landfill root cause (intent.md:7). The H1 should keep the change name as a human title (harmless), but the instructions output must additionally surface `existing_specs` (already an optional context source per `src/context/context-engine.ts:39-42,289-290`, though currently only exposed as raw file content, not as a distinct capability-slug list on `InstructionOutput`) and require the author to place the marker or name an existing slug before the artifact counts as valid input to `complete.ts`.

**2. Completeness-gate placement** — before merge/lock (earliest), vs. after merge dry-run before gates, vs. after gates.
`Finalizer.finalize()` (finalizer.ts:31-62) currently does zero artifact-status inspection; it calls `this.artifactStore.getChange(changeName)` at line 32 purely to read `metadata.workflow` (line 40). `metadata.artifacts` (schema: `ArtifactStatusSchema` in `src/schemas/change-metadata.ts:3-10`, values `pending|ready|in_progress|complete|failed|skipped`) is loaded but never checked — `'complete'` is the only terminal/accepted state per spec.md:79. The check needs only `metadata` (already in memory) and the workflow's artifact list (already loaded via `workflowEngine.loadWorkflow` at line 40) — no lock, no merge output — so it belongs as the very first step, before the `SpecMerger.merge` call at line 50. **Live evidence of the gap**: `spec/archive/2026-07-14-fix-metta-guard-edit-hook-blocks-edit-write-files-outside/.metta.yaml` records `artifacts: { intent: complete, implementation: complete, verification: ready }` yet the change is archived — proving finalize shipped with `verification` stuck at `ready`. `tests/finalizer.test.ts` corroborates the gap structurally: every test calls `artifactStore.createChange(...)` (which defaults all artifacts to `pending`/`ready`, `src/artifacts/artifact-store.ts:36-42`) and then calls `finalizer.finalize(...)` directly — **no test ever calls `markArtifact(..., 'complete')` first**, and finalize still succeeds. No existing test asserts finalize *refuses* on incomplete artifacts.

**3. Merge ordering** — dry-run→gates→write→archive (chosen) vs. write→gates→rollback-on-fail.
`SpecMerger.merge` (spec-merger.ts:27-114) already threads a `dryRun` boolean through every write site (`!dryRun` guards at lines 57, 99) and *does* return computed `merged`/`conflicts` in dry-run mode without writing — so dry-run-only conflict detection is already supported with no merger refactor. The only change needed: `Finalizer.finalize()` currently calls `merger.merge(changeName, metadata.base_versions, dryRun)` once (finalizer.ts:50), passing through the caller's `dryRun`; it must instead **always** dry-run first for conflict detection, run gates, then call `merge` a second time with `dryRun=false` only after gates pass — i.e., two `merge()` invocations, not a merger rewrite. Rollback-on-fail was rejected: it requires snapshot/restore of arbitrary capability spec files and lock files, more moving parts than simply deferring the write, and spec.md:76-90 explicitly prescribes the dry-run-first ordering. **Surprise**: the CLI's exit-code ordering (`src/cli/commands/finalize.ts:59-97` checks `!result.gatesPassed` before checking `result.specMerge.status === 'conflict'` at line 100) means a *current* conflict result (which forces `gatesPassed: false`, `gates: []` at finalizer.ts:52-62) is misreported today as "Quality gates failed" with an empty gate list instead of "Spec merge conflicts detected" — this ordering bug should be fixed alongside the reorder, not left latent.

**4. ADDED idempotency key** — name-only vs. name+content-hash vs. always-skip.
`splitRequirements()` (spec-merger.ts:238-282) already keys sections by requirement **name** only, and `parseSpec`/`parseDeltaSpec` compute a `hash` field per requirement (spec-parser.ts:112, 212) but that hash is not consulted by the MODIFIED/RENAMED/REMOVED branches for equality — only for `sections.has(name)` lookups. Content-hash comparison would let a name-only-matching-but-textually-different re-add produce a silent conflict-vs-noop ambiguity the spec doesn't ask for; finalize-ship spec.md:47 explicitly says "check whether a section with the same requirement name already exists ... using the same lookup the MODIFIED/RENAMED/REMOVED branches use" — i.e., name-only, no-op on match. This is consistent and requires the smallest diff: add one `sections.has(delta.requirement.name)` guard to the ADDED branch (spec-merger.ts:147) mirroring the existing MODIFIED check at line 161.

**5. Trivial workflow contract (US-4)** — align `generates` to instructions vs. align instructions to `generates`.
`src/templates/workflows/trivial.yaml:22-28` declares verification `generates: summary.md`; `src/templates/artifacts/verify.md` (the rendered instructions) titles the artifact `# Verification: {change_name}` and never names a target filename in its body. `complete.ts:94` resolves `generates` from the workflow definition (`artifactDef?.generates ?? \`${artifactId}.md\``) — so the *declared* target is `summary.md`, but nothing in `verify.md` tells the agent to write there. Live reproduction: `spec/archive/2026-07-14-fix-metta-guard-edit-hook-blocks-edit-write-files-outside/` contains `verification.md` (matching the `${artifactId}.md` fallback pattern an agent would naturally infer from the H1/artifact id), not `summary.md` — and the archived `.metta.yaml` confirms `verification: ready`, never `complete`, i.e. `metta complete verification` never succeeded for this change and finalize proceeded anyway (same evidence as #2). Fix direction: since `verify.md`'s own H1 and content model (`## Summary` section, `{implementation_summary}` placeholder) already conceptually matches "a summary," the lower-cost fix is to make the instructions explicitly direct the agent to save the file as `summary.md` (add explicit output-path instruction), not to rename `generates` — `output_path` is already computed correctly by `InstructionGenerator.generate` (instruction-generator.ts:107) from `params.artifact.generates`, so the generator layer is already right; only the template and/or the agent's attention to `output_path` needs fixing. `quick.yaml:22-28` has the identical mismatch and should get the same fix for consistency, though it is out of this change's named scope (spec.md doesn't mention quick.yaml) — flag as a likely follow-on.

**6. Test coverage** — existing files: `tests/finalizer.test.ts` (Finalizer, no completeness-gate test, no dry-run-then-write-ordering test), `tests/spec-merger.test.ts` (SpecMerger — covers ADDED-into-new-capability, MODIFIED idempotency across two `merge()` calls, RENAMED, REMOVED-missing-conflict, but **no test re-applies an ADDED delta into an already-existing capability spec** — the exact US-5 gap), `tests/cli-complete.test.ts` and `tests/complete-stamps-timings.test.ts` (complete.ts, cover artifact-completion mechanics but not the spec-delta target-capability gate at complete.ts:157-175 specifically, nor a new-capability-marker scenario). No dedicated `complete-spec-gate` test file exists. A finalize-with-incomplete-artifacts test does not exist today (confirmed by reading all of `tests/finalizer.test.ts`).

### Rationale

Every fix should be the smallest change that satisfies spec.md's explicit prescriptions and reuses code already proven correct: the marker is spec.md's own design and needs no schema change; dry-run merge needs no `SpecMerger` rewrite because `dryRun` plumbing already exists end-to-end; the completeness gate is one new step using data already in hand; the ADDED idempotency fix is a one-line guard mirroring an existing pattern three branches over. The trivial-workflow fix is directional (instructions → contract) because the generator/`output_path` layer is already correct and only the template text is stale.
