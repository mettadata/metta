# Research: fix-forked-metta-skills-return-early-while-their-background

## Decision: Approach 1 (rule in metta-skill-host.md as single source, mirrored one-line pointer in each skill; PreToolUse hook keys off tool_input.run_in_background + event.agent_type; mtime fallback only on the EPERM/ambiguous branch of isPidAlive; new checkFinalizeLockStale() exported from finalize-lock.ts and called from status.ts/next.ts)

### Approaches Considered

1. **[SELECTED] Single-source contract in `metta-skill-host.md` + one-line pointer per skill; hook reads `tool_input.run_in_background`; mtime fallback gates only the ambiguous branch; lock-staleness helper lives in `finalize-lock.ts`.**
   - The synchronous-completion rule is authored once, in `.claude/agents/metta-skill-host.md`, because every one of the six `context: fork` skills declares `agent: metta-skill-host` in frontmatter (`.claude/skills/metta-ship/SKILL.md:6`, `metta-issue/SKILL.md:6`, `metta-fix-issues/SKILL.md:7`, `metta-quick/SKILL.md:7`, `metta-auto/SKILL.md:7`, `metta-propose/SKILL.md:7`) — the host file's prompt content is loaded into every fork's context regardless of which skill runs. `metta-skill-host.md` today is 21 lines with a `## Rules` section (`.claude/agents/metta-skill-host.md:16-21`) that already governs turn-ending behavior ("When the skill completes, return a short summary..."), the natural home for the new hard rule. Each `SKILL.md` gets a short one-line reference (not a restatement) so grep-based audits (per US-1's Independent Test Criteria) still find the rule text without 6x duplication of the prose itself. Note: none of the six `SKILL.md` files currently contain literal "background" / "I'll wait" / "in progress" text (`grep -ln "background\|I'll wait\|notified when\|in progress\|running in the"` over `.claude/skills/*/SKILL.md` returned zero matches) — the offending phrasing observed in the incident was model-improvised narration, not template text, so item 1 is a *preventive* rule addition, not a text replacement in the skills themselves. The one skill with an actually-backgroundable step, `metta-ship`'s finalize dry-run (`.claude/skills/metta-ship/SKILL.md:13-14`, invoked as a plain foreground `Bash` call with no `run_in_background` flag today), needs one explicit "this blocks; do not treat it as backgrounded" line added at that step.
   - Hook: `metta-guard-bash.mjs` parses the PreToolUse event as `JSON.parse(stdin)` (`.claude/hooks/metta-guard-bash.mjs:135-137`) and already reads `event.tool_input?.command` (line 142) and `event.agent_type` (line 106, `isTrustedSkillCaller`). The event is Claude Code's standard PreToolUse payload for the `Bash` tool, whose `tool_input` carries every parameter passed to the tool call — `command`, and, when set, `run_in_background` — as sibling keys of the same `tool_input` object already being read for `command`. There is no separate event shape to reconcile; the new check is `event.tool_input?.run_in_background === true` alongside the existing `agent_type` check, added as a new early branch before the existing `classify()`/`offender` pipeline (which is keyed on `metta <subcommand>` tokenization and would not otherwise see a background-Bash call running some other command, e.g. a `sleep` or long CLI invocation with no `metta` prefix at all). The rejection must therefore be its own branch — sibling to the `if (event.tool_name !== 'Bash') process.exit(0)` guard at line 137 — not folded into `classify()`/`offender`, because `run_in_background` is orthogonal to the `metta <subcommand>` allow/block logic and can be true on commands the tokenizer never inspects.
   - Lock: `finalize-lock.ts`'s `isPidAlive` (lines 33-41) treats `EPERM` as "alive" (line 38) — that is precisely the ambiguous case the mtime fallback (per spec.md's "Finalize Lock Staleness Fallback Via Mtime") must catch, since a live-but-inaccessible pid and a dead-recycled pid both surface as `isPidAlive === true` today with no way to tell them apart. The lock file already records `startedAt` (`FinalizeLockSchema` at `src/schemas/finalize-lock.ts:3-7`: `{ pid, startedAt, change }`, `.strict()`), but `startedAt` is an ISO string set at acquisition (`finalize-lock.ts:77`) — the mtime fallback per spec text is keyed on the lock *file's* mtime (`fs.stat(lockPath).mtime`), not `startedAt`, and the state store's own precedent (`STALE_LOCK_THRESHOLD_MS = 60_000` at `src/state/state-store.ts:24`, applied to file age at `state-store.ts:128-132`) uses file age the same way — so the new logic reads `lockPath`'s stat, not the JSON body, keeping both signals independent and re-using the existing constant name/threshold value for consistency.
   - Status/next: a new exported `checkFinalizeLockStale(projectRoot, change): Promise<{ stale: boolean; reason?: 'dead-pid' | 'mtime-expired' }>` lives in `finalize-lock.ts` itself (co-located with `isPidAlive` and the lock schema it depends on, avoiding a new module), imported by both `status.ts` and `next.ts`. This keeps the additive contract in one place testable independently of CLI wiring, and both commands call it identically before their existing print paths — `status.ts`'s `printChangeStatus` (line 93) gets one appended line when stale; `next.ts`'s `allComplete` branch (lines 95-103, which currently routes straight to `metta finalize`) gets a stale check inserted before emitting the `next: 'finalize'` route.

2. **Duplicate the synchronous-completion rule verbatim into all six `SKILL.md` files instead of centralizing in `metta-skill-host.md`.**
   - Pro: each skill is self-contained; a reviewer reading one `SKILL.md` sees the full rule without following a reference to the agent file.
   - Con: six-way duplication the intent.md's own impact section calls out as a "6x duplication" risk to avoid; any future wording fix (e.g. after another incident) requires six synchronized edits instead of one, and drift between copies is exactly the failure mode `tests/agents-byte-identity.test.ts`'s sibling test (`template-deploy-sync.test.ts`) exists to catch for template/deployed pairs — this would introduce an analogous but untested drift risk across skill files with no equivalent gate. Rejected in favor of centralizing in the always-loaded host file.

3. **Enforce background-Bash rejection via a general `Stop`/`SubagentStop` hook instead of (or in addition to) the PreToolUse `run_in_background` check.**
   - Pro: would also catch a fork ending its turn with a dispatched Agent still pending, which the PreToolUse Bash hook cannot see.
   - Con: explicitly out of scope per intent.md's "Out of Scope" section — `SubagentStop` hook semantics are called out as not reliably available across supported Claude Code versions for this project. Rejected; matches intent.md's explicit scoping, not just a preference.

4. **Put the mtime staleness check as a hard replacement for `isPidAlive`'s EPERM-as-alive default, rather than an additive fallback gated on ambiguity.**
   - Pro: simpler — one check (mtime) instead of two conditions.
   - Con: spec.md's scenarios (`spec.md:50-55`, "Fresh lock with a confirmed live owner is respected") require a fresh, live-owned lock to still throw `FinalizeLockError` even though EPERM is inherently ambiguous by nature — an unconditional mtime-first check would incorrectly reclaim a fresh lock owned by a process the current user merely lacks permission to signal. Rejected; the mtime check must be additive and only consulted when pid-liveness is ambiguous (EPERM) or would otherwise miss a recycled pid, per spec.md lines 34-40.

### Rationale

Approach 1 follows the codebase's existing patterns rather than introducing new ones: `metta-skill-host.md` is already the single point every fork skill loads (confirmed by frontmatter grep across all six `SKILL.md` files), so a rule stated there is structurally guaranteed to apply everywhere without duplication, consistent with how the hook's `isTrustedSkillCaller` already treats `agent_type` as the one caller-identity signal shared by all forks (`metta-guard-bash.mjs:105-107`). The hook change is additive — a new branch reading a `tool_input` field the event already carries — with no restructuring of `classify()`/`offender`, matching intent.md's explicit constraint that `SKILL_ENFORCED_SUBCOMMANDS` and audit-log behavior stay unaffected. The lock and status/next changes reuse the state store's proven 60s mtime-staleness convention and the lock module's own existing schema/constants rather than inventing a new threshold or a new module, and land the new capability (`checkFinalizeLockStale`) exactly where its dependencies (`isPidAlive`, `FinalizeLockSchema`) already live.
