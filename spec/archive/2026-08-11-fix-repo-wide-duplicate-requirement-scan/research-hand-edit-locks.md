# Research: Hand-edit spec.lock files directly

## Approach

Dedupe the three spec.md files the same way, but repair each `spec.lock` by hand: delete the duplicated requirement entries from the YAML, bump `version`, and recompute/patch the top-level `hash` manually.

## Findings

- The lock's top-level `hash` is `hashSpec(parsedSpec)` (`src/specs/spec-parser.ts` / `spec-lock-manager.ts:47`) — a content hash that cannot be correctly recomputed by hand without re-running the parser anyway.
- Hand-editing state files conflicts with the project constitution's "No unvalidated state writes" convention — the StateStore Zod-validates on write, and bypassing it forfeits that guarantee.
- The prior statusline repair explicitly called out "Lock regenerated by the real code path, not hand-edited" as a verification point; reviewers would flag hand-edited locks.

## Tradeoffs

- **Pro:** no tsx invocation needed.
- **Con:** top-level hash cannot be produced by hand; risks stale/incorrect hash that later triggers spurious drift detection; violates project conventions; weaker evidence trail.

## Verdict

Not viable for the hash field; strictly dominated by the code-path regeneration approach.
