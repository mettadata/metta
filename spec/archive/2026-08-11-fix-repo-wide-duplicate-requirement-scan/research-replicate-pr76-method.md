## Approach

Reuse the exact method proven in `spec/archive/2026-08-11-fix-statusline-spec-duplicated-requirements/summary.md`:

1. **Dedupe** — diff-verify each duplicate block against its first occurrence, then delete the later copies with line-range edits. (Already verified for this change: all copies byte-identical modulo trailing blank lines.)
2. **Lock regen via the real code path** — a small tsx script per capability: `parseSpec(readFileSync(spec.md))` → `new SpecLockManager('<root>/spec').update(capability, parsed)`. `update()` bumps `version`, recomputes `hash` via `hashSpec`, and rewrites the requirement inventory (`src/specs/spec-lock-manager.ts:55-67`). Per-requirement hashes should come out unchanged, confirming content identity — the same evidence PR #76 cited.
3. **CLAUDE.md** — `metta refresh` regenerates the Active Specs counts.

## Findings from code inspection

- `SpecLockManager.update()` reads the existing lock only to increment `version`; a corrupted lock that fails Zod falls back to version 1. Current corrupted locks (e.g. install-init, version 11, with duplicated requirement entries) appear schema-valid, so version increments normally.
- `createFromParsed` emits `status: 'draft'`, `source: 'change'` — identical to what the statusline repair produced, so no schema drift.
- The merger idempotency guard at `src/finalize/spec-merger.ts:177` means no code change is needed; this is purely data repair.

## Tradeoffs

- **Pro:** proven once already; lock generated by the project's own code path (no hand-edited YAML, honoring "no unvalidated state writes"); evidence trail (unchanged per-requirement hashes) is strong.
- **Con:** requires running tsx scripts, slightly more setup than hand-editing — negligible.
