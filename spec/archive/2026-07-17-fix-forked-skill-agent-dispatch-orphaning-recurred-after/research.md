# Research: fix-forked-skill-agent-dispatch-orphaning-recurred-after

## Decision: Approach B — forced-synchronous `Agent` dispatch via a `PreToolUse` hook scoped in `metta-skill-host.md` frontmatter, promoted to primary; the `SubagentStop`-ledger design (Approach A) is deferred pending one live experiment; the contract-only recovery protocol (Approach D) lands regardless as the floor.

### Approaches Considered

**A. `SubagentStop`-blocking pending-dispatch ledger (the intent's original "Primary").** `SubagentStop` is a real, documented event: it fires "when a subagent finishes," carries `session_id`, `transcript_path`, `cwd`, `hook_event_name`, and — only when the hook fires inside a subagent call — `agent_id`/`agent_type`, plus `last_assistant_message`[^1]. It can block via exit code 2 ("prevents the subagent from stopping (continues working)") or `{"decision":"block","reason":"..."}`, and the `reason` is fed back to the subagent so it keeps working instead of returning[^1]. A `Stop` hook declared in an agent's frontmatter is "automatically converted to `SubagentStop` events" for that agent[^2] — confirming the mechanism intent.md cited. The design requires a ledger written by a `PreToolUse`/`PostToolUse` pair on the `Agent` tool. This is where the plan breaks down: `agent_id` is present "only when the hook fires inside a subagent call" and identifies *that* subagent[^1] — so a `PreToolUse` firing inside the fork when it dispatches a child shares its `agent_id` with the fork's own later `SubagentStop`, not with the child's `SubagentStop`. That happens to be exactly the correlation the ledger needs (per-fork counters, not per-child identity), so correlation is *not* the blocker research initially flagged. The real unresolved fact is **timing**: docs state `PostToolUse` fires "after a tool call succeeds," but do not specify whether a background-dispatched `Agent` call "succeeds" at launch or at actual child completion, and no `PostToolUse`-for-`Agent` example or field list is published[^1]. If `PostToolUse` fires at launch (plausible, since `TaskCompleted` exists as a separate documented event for background/task completion[^3]), the ledger clears immediately and never blocks anything — a silent no-op, not a fail-safe.

**B. Forced-synchronous dispatch via `PreToolUse` policing of `Agent` dispatch shape (the intent's "Secondary," reclassified here as primary).** As of Claude Code v2.1.198, subagents run in the background by default; a subagent-definition's `background` frontmatter field can force always-background, and when unset "Claude chooses"[^2]. `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` "disable[s] all background task functionality, including the `run_in_background` parameter on Bash and subagent tools"[^4] — this is the documentary confirmation that the `Agent` tool's `tool_input` carries a `run_in_background`-style field in the same family as Bash's, resolving fact (d): yes, an async/background flag exists in the dispatch shape, not merely a harness-side behavior invisible to `tool_input`. "Foreground subagents block the main conversation until complete"[^2] — meaning if a `PreToolUse` hook denies (or force-rewrites) any `Agent` dispatch from a verified `metta-*` fork caller that isn't foreground, the dispatching tool call itself cannot return control to the fork until the child is actually done, by the runtime's own blocking semantics. This is structurally the same enforcement metta-guard-bash.mjs already applies to Bash's `run_in_background: true`[^1], just retargeted at the `Agent` tool — no ledger, no correlation, no timing ambiguity. Note: `context: fork` in a skill's frontmatter is Claude Code's "run this skill in its own subagent context" feature[^5], unrelated to the separate `CLAUDE_CODE_FORK_SUBAGENT` conversation-forking feature that removes `run_in_background` entirely in *that* mode[^2] — metta's forks are ordinary named-subagent (`agent: metta-skill-host`) dispatches, so the `run_in_background` parameter is present and denyable.

**C. Both A and B, layered.** Rejected for v1: B alone already satisfies spec.md's mechanism-(b) branch ("constrain `Agent` dispatches issued from a fork context to complete synchronously before the dispatching call itself returns control to the fork") without any undocumented behavior. Layering in A today would ship a hook whose clearing condition (`PostToolUse` timing) is unverified — exactly the risk research discipline exists to catch. A is not deleted from the design space; it is deferred behind the experiment below.

**D. Contract-only recovery protocol (the intent's "Floor").** Always lands regardless of A/B, per spec.md's third requirement (Residual Orphaning Recovery Protocol). Not mechanically enforced, so it cannot alone satisfy the Completion Guarantee requirement, but it is the correct backstop for any gap B does not cover (see Residual Threat below).

### Rationale

Approach B is chosen as primary because every fact it depends on is directly quoted from official docs — the `run_in_background`-family parameter on the `Agent` tool[^4], forced-foreground blocking semantics[^2], and the `hooks:` frontmatter scoping mechanism[^2][^5] — while Approach A depends on one fact (`PostToolUse`-for-`Agent` timing) that is not published anywhere in the hooks reference or subagents guide. Both skill frontmatter and agent frontmatter document a `hooks:` field ("Hooks scoped to this skill's lifecycle"[^5]; "Lifecycle hooks scoped to this subagent"[^2]), and the hook-location table states frontmatter hooks apply "while the skill or agent is active"[^2]. Since all six fork skills declare `agent: metta-skill-host`, declaring the new `PreToolUse` (matcher `Agent`) hook — and, as defense-in-depth, a `Stop` hook (auto-converted to `SubagentStop`[^2]) that simply logs/no-ops today — directly in `.claude/agents/metta-skill-host.md` frontmatter scopes enforcement to exactly the fork host with zero risk of firing for `Explore`, `Plan`, or any non-`metta-*` subagent, without needing the `event.agent_type` self-filter metta-guard-bash.mjs currently relies on for its global `.claude/settings.json` registration. This is architecturally cleaner than the intent's global-registration assumption and should be corrected in design.md.

**Live experiment required before implementation locks in Approach A:** in a real Claude Code session, dispatch a `metta-*`-fork-caller `Agent` call with `run_in_background` unset (post-v2.1.198 default), and observe whether `PostToolUse` for that call fires at dispatch (near-instant) or at the child's actual completion (elapsed time matching the child's real work). If instant, `PostToolUse`-based ledger-clearing is unsound and Approach A must be dropped or redesigned around a different clearing signal (e.g., a `SubagentStop` seen for the *child's own* `agent_type`, using the `SubagentStop` matcher's "agent type" filter[^2] rather than `PostToolUse`). This experiment is deferred to design/implementation and does not block landing Approach B.

**Residual threat:** docs mention Claude can be asked mid-session to "run a task in the background" and Ctrl+B can background an already-foreground task interactively[^2] — both are session-UI-level re-backgrounding paths, not `tool_input` shapes visible to `PreToolUse`. If either applies to a fork-initiated dispatch after `PreToolUse` already forced it foreground, B's guarantee could be defeated outside the dispatch-shape check. Approach D (contract recovery protocol) and the audit log (US-4) exist precisely to catch and record that residual case; spec.md does not need amendment — its mechanism-(b) branch already anticipates exactly this shape.

### Test surface

The existing `tests/metta-guard-bash.test.ts` harness (`spawnSync('node', [hookPath], { input: JSON.stringify(payload) })`, asserting exit code and stderr) is event-shape-agnostic: it works identically for a synthetic `PreToolUse`-on-`Agent` payload (`tool_name: 'Agent'`, `tool_input: { subagent_type, prompt, run_in_background }`, `agent_type`) and, if Approach A is later adopted, a synthetic `SubagentStop` payload (`hook_event_name: 'SubagentStop'`, `agent_id`, `agent_type`, `last_assistant_message`) — no live Claude Code runtime is needed for hook-script unit tests; only the timing experiment above requires one.
