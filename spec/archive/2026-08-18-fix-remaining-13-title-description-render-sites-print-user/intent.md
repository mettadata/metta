# fix-remaining-13-title-description-render-sites-print-user

## Problem

Issue, gap, backlog, milestone, roadmap, and user-story titles and descriptions are user-controlled strings: they originate from markdown files under `spec/` that may be authored by hand, generated by AI subagents, or imported from external sources. When the CLI echoes these strings back to a TTY without sanitization, embedded ANSI/VT escape sequences and control bytes can repaint the terminal, move the cursor, rewrite the window title, inject OSC 8 hyperlinks, or spoof surrounding CLI output — a terminal-injection class defect.

The `fix-follow-ups` change (PR #86) added `src/util/sanitize-text.ts` (`stripControlSequences`) but, per its design ADR-1, deliberately wrapped only the two defect sites reported at the time: `backlog.ts:76` (backlog list rows) and `milestone.ts:177` (milestone show issue rows). A follow-up audit (issue `remaining-13-title-description-render-sites`, severity minor, priority medium) found the same class of defect at every other title/description render site. Verified in this worktree, the unsanitized sites are:

Two blockers prevent a mechanical wrap-everything fix today:

1. `stripControlSequences` strips **all** C0 controls including `\n`, so wrapping a multi-line description body would collapse it onto one line. A newline-preserving variant is required for the four body sites.
2. Several show blocks print additional free-text fields from the same untrusted source on adjacent lines (`fix-issue.ts:89–90` captured/context, `gaps.ts:35–37`+ and `fix-gap.ts:95–99` source/claim/evidence/impact/relatedSpec). Sanitizing the title but leaving the claim line injectable would fix only half of each screen.

Who is affected: any developer running `metta issue list/show`, `metta fix-issue`, `metta gaps`, `metta fix-gap`, `metta roadmap`, `metta backlog show`, `metta milestone show`, or story validation against a repo containing hostile or accidentally escape-laden spec content — including repos where AI subagents author issue/gap markdown.

## Proposal

1. **Add a newline-preserving sanitizer variant** to `src/util/sanitize-text.ts`: `stripControlSequencesMultiline(text)` (exact name settled at design time), which preserves `\n` line breaks but strips every other control sequence and control byte per the existing `CONTROL_SEQUENCE_RE` coverage (CSI, OSC, DCS/SOS/PM/APC, two-byte Fe escapes, bare C0/C1/DEL — including `\r`, so CRLF input normalizes to LF). It reuses the existing regex/logic rather than duplicating it, stays pure and idempotent, and passes printable text (all Unicode at or above U+00A0) through unchanged.

2. **Wrap each unsanitized render site at the render edge** — inside the `console.log` template expression, exactly as the two PR #86 sites do:
   - Single-line sites (12 rows in the first table above): wrap with `stripControlSequences(...)`.
   - Multi-line body sites (4 rows in the second table): wrap with the newline-preserving variant.
   - Same-block free-text fields printed alongside the wrapped titles (`fix-issue.ts` captured/context; `gaps.ts` and `fix-gap.ts` source/claim/evidence/impact/relatedSpec; `roadmap.ts` note): wrap with `stripControlSequences(...)`. These are the same untrusted strings from the same markdown files rendered on adjacent lines; excluding them would leave the defect half-fixed per screen. This is a deliberate widening of the issue's literal ~13-site list, at near-zero cost.

3. **JSON output paths stay byte-faithful.** Only the human-readable (`console.log` to TTY) branches change; every `outputJson(...)` branch continues to emit the stored strings unmodified so machine consumers see exact file content.

4. **Tests** in `tests/sanitize-text.test.ts` for the new variant (newline preservation, CR stripping, escape-sequence coverage parity with the single-line helper, idempotence, Unicode pass-through), plus command-level render tests asserting that titles/descriptions containing escape sequences are printed stripped in text mode and unmodified in `--json` mode for at least one list site, one heading site, and one multi-line body site.

## Impact

- **Human-readable CLI output changes** for the affected commands when — and only when — the underlying spec markdown contains control bytes or escape sequences: those bytes are now removed before printing. Clean content renders byte-identically to today, so normal users see no difference.
- **Multi-line descriptions** keep their line structure (LF preserved); CRLF-authored content renders with LF only. This is the only intentional rendering change for non-hostile input.
- **JSON output is untouched** — no impact on scripts, skills, or subagents consuming `--json`.
- `src/util/sanitize-text.ts` gains one exported function; the existing `stripControlSequences` signature and behavior are unchanged, so the two PR #86 call sites are unaffected.
- Eight command files under `src/cli/commands/` gain an import and per-site wrapping; no control flow, exit codes, error handling, or Commander wiring changes.
- Test surface grows in `tests/sanitize-text.test.ts` and the relevant command test files, maintaining the near 1:1 test-to-source ratio.

## Out of Scope

- **Sanitizing JSON output** — explicitly excluded; JSON stays byte-faithful by design (matches PR #86 ADR-1).
- **Sanitizing at write time or in the stores** — we do not reject, normalize, or rewrite escape sequences when issues/gaps/backlog markdown is created or parsed. Files on disk remain exact; sanitization happens only at the terminal render edge.
- **Slug, severity, status, priority, and other schema-constrained fields** — these are Zod-validated enums or constrained identifiers, not free text; wrapping them adds noise without closing any hole.
- **Render sites outside the eight files audited by the issue** (e.g. `status.ts`, `progress.ts`, `changes.ts`, `tasks-renderer.ts`) — if a later audit finds unsanitized user-controlled prints there, that is a new issue, not silent scope growth here.
- **A general markdown-to-terminal renderer or width/truncation handling** — this change strips control sequences only; it does not reformat, wrap, or truncate text.
- **Changing the existing `stripControlSequences` regex coverage** — the escape-sequence classes stripped are exactly those PR #86 shipped; broadening or narrowing coverage is a separate concern.
- **Lint rule or CI guard enforcing sanitized rendering** — worth considering as a follow-up backlog item, but not part of this fix.
