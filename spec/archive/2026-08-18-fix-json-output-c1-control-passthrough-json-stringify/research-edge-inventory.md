One nuance the implementation must preserve: `config.ts:58` is reached in **text mode** (no `--json`), yet it prints JSON. The spec's scenario ("config get escapes C1 controls identically to outputJson") is satisfiable by wrapping the `JSON.stringify(value, null, 2)` expression in the helper; the `String(value ?? ## 3. Recommended test plan

Existing convention check: `src/util/sanitize-text.ts` → `tests/sanitize-text.test.ts` (repo-root `tests/`, same basename, `.test.ts`). Util modules are *not* barrel-exported (only `util/archive-dirs.js` appears in `src/index.ts:16`); `sanitize-text` is imported directly by consumers. Follow that precedent — no barrel change needed. A minority of newer tests are colocated in `src/` (`src/config/build-stamp.test.ts`, `src/finalize/finalize-lock.test.ts`), but the util-helper precedent is `tests/`, and the task-relevant CLI suites all live in `tests/`.

1. **New helper + unit test (spec req 3 scenarios):**
   - Source: `src/util/escape-json-controls.ts` exporting `escapeJsonControls(jsonText: string): string`.
   - Test: `tests/escape-json-controls.test.ts` (1:1 with source). Cases: boundary precision (U+007E and U+00A0 intact; U+007F → ``; U+009F → ``; U+009B → ``), empty string, idempotency (`escapeJsonControls(escapeJsonControls(x)) === escapeJsonControls(x)` — trivially true since output contains no chars in range), multi-byte neighbors intact (e.g. `é`, CJK, emoji surrogate pairs), full `JSON.stringify` round-trip property (`JSON.parse(escapeJsonControls(JSON.stringify(s))) === s` for hostile `s`), and a structural-safety case (an object whose *key* contains U+009B, proving post-stringify replacement cannot corrupt JSON grammar).

2. **CLI-level U+009B/U+007F round-trip (spec req 1 scenarios 1-2 + req 2 scenario 1):** extend `tests/cli-issue-backlog.test.ts`, `describe('render-edge sanitization (text stripped, JSON byte-faithful)')` (starts ~:471). Two options; recommend (a):
   - (a) Add `\x7f` to the existing `HOSTILE_ISSUE` description line and add a sibling `it('issues show --json escapes DEL and C1 in the JSON text')` in the same block: run `--json issues show placeholder`, assert `jsonRes.stdout` does **not** match `/[\x7f-\x9f]/`, **does** contain the literal six-char sequences `` and `` (as `stdout.includes('\\u009b')`), and `JSON.parse` still round-trips both fields byte-identically. Leaves the existing byte-faithful `it` untouched (spec req 2 scenario 2 demands they pass *unmodified* — adding `\x7f` to the shared fixture technically edits the fixture the unmodified test reads; if the verifier reads "unmodified" strictly, use a separate seeded issue in the new `it` instead of touching `HOSTILE_ISSUE`). Safer strict reading: **seed a second hostile issue inside the new test** and leave `HOSTILE_ISSUE` alone.
   - (b) Mirror the same new `it` in `tests/cli-gaps.test.ts` — optional redundancy; the shared-helper design makes one CLI-level proof sufficient.
3. **Error-envelope scenario (spec req 1 scenario 3):** unit-level in `tests/cli-helpers.test.ts` — the existing `console.log` spy pattern (`:85-86`) makes this cheap: call `outputJson({ error: { message: 'x\x9by' } })` (or drive `handleError` with an error whose message embeds `\x9b`), assert printed text has no raw `\x9b` and contains `\\u009b`, and `JSON.parse` round-trips.
4. **config get edge (spec req 3 scenario 1):** extend `tests/config-set-edit.test.ts` — seed a config key whose object value embeds `\x9b`, run text-mode `config get <key>` and assert stdout is C1-free with the `` escape present; run `--json config get` for the outputJson path parity.
5. **tasks --json edge (spec req 3 scenario 2):** extend `tests/cli-tasks.test.ts` `--json` test (~:63) — a `tasks.md` fixture with `\x9b` in a task label; assert stdout C1-free + parse fidelity.
6. **Stored-file invariance (spec req 2 scenario 3):** already the established pattern (`cli-milestone.test.ts:240-253` bytes-before/after) — fold a bytes-equal check into the new issue-backlog `it` (read `spec/issues/<slug>.md` before/after the `--json` run).

## 4. Verdict notes for the synthesizer

- **Intent audit confirmed complete**: exactly three stdout JSON edges — `src/cli/helpers.ts:234` (`outputJson`, incl. all error envelopes), `src/cli/commands/config.ts:58` (text-mode object-value print; wrap only the `JSON.stringify` branch, never the scalar `String(...)` branch), `src/cli/commands/tasks-renderer.ts:82` (`renderJsonPlan`, success path only — tasks errors already funnel through `outputJson`). All file-write stringify sites (install/state-store/finalize-lock/version-file) and hook-template sites must NOT get the escape.
- **No existing test breaks; none need modification.** All four named byte-faithful suites assert `JSON.parse`d values; all raw-`\x9b` negative assertions target text mode. The "existing suites pass unmodified" spec scenario is satisfiable with zero edits to them — prefer seeding a fresh hostile fixture in new `it` blocks over mutating the shared `HOSTILE_ISSUE`/`HOSTILE_GAP` constants, to keep "unmodified" true under the strictest reading.
- **Helper placement**: `src/util/escape-json-controls.ts` + `tests/escape-json-controls.test.ts`, direct imports (no barrel change), matching the `sanitize-text` precedent. Regex `/[-]/g` with a `\uXXXX` formatter is sufficient; the range contains no surrogate halves, so code-unit replacement is code-point safe.
- **Post-stringify replacement safety holds**: in `JSON.stringify` output all structural characters and inserted indentation are ASCII < 0x7F, so U+007F–U+009F can occur only inside string literals (keys or values) — global replacement cannot corrupt structure. Worth one explicit unit case (hostile key) to pin this.
- **Follow-up flag (not this change)**: `src/cli/commands/install.ts:151` interpolates a user-influenced settings value into a stderr warning without `sanitize-text` — a text-mode render-edge gap in the PR #86 lineage; recommend logging as a separate minor issue.
