# model-tier-routing-orchestration-agents-top-tier-models

## Problem

Metta's subagent model assignment is currently the inverse of what a cheap-execution strategy requires, and the assignment is frozen at the wrong layer — agent-file frontmatter — instead of being computed per change.

Today, five agent templates in `src/templates/agents/` carry `model: sonnet` in frontmatter: `metta-architect.md`, `metta-planner.md`, `metta-proposer.md`, `metta-researcher.md`, and `metta-specifier.md` (mirrored byte-identically in the deployed `.claude/agents/`). These are exactly the **planning-phase** agents — the ones that author intent, spec, architecture, and task decomposition. Every execution-and-safety-phase agent (`metta-executor.md`, `metta-reviewer.md`, `metta-verifier.md`, `metta-product.md`, `metta-discovery.md`, `metta-constitution-checker.md`, `metta-skill-host.md`) carries no `model:` key at all, so it inherits whatever top-tier model the parent session is running under.

This is backwards for two independent reasons, both evidenced by 2026-07 session data:

1. **Cost is spent in the wrong place.** Executor and verifier subagents consumed roughly 60% of subagent tokens in the observed week, and they run at the (expensive) inherited top-tier model even though execution against a well-specified task list and mechanical verification against spec scenarios are exactly the kind of well-specified, low-ambiguity work a cheaper model tolerates well.
2. **Quality risk is spent in the wrong place.** Both of the week's real design bugs were authored by the (deliberately downgraded) sonnet planning agents — proposer, specifier, architect, planner — and were only caught later, more expensively, by top-tier executors reading an ambiguous or wrong spec. Planning artifacts (intent, spec, architecture, task breakdown) set the ceiling on everything built from them; downgrading the model that authors them is the highest-leverage place *not* to cut cost.

Compounding this, `instructions.ts` / `instruction-generator.ts` currently emits an `agent` block (`name`, `persona`, `tools`, `rules`) with no `model` field at all (`src/context/instruction-generator.ts:13-18`), and no skill's `Agent(...)` invocation pattern passes a `model` parameter (confirmed by inspecting `.claude/skills/*/SKILL.md`, e.g. `metta-execute/SKILL.md:36-45`). So even where agent-file frontmatter carries `model: sonnet`, there is no mechanism today for a project's model choice to vary per change, per workflow tier, or in response to a runtime signal like a STOP report or a verification failure — every routing decision is a static, file-level default with no config surface and no dynamic override path.

Everyone running metta today — every project's orchestration sessions — is affected: they are silently paying top-tier-model cost for planning agents that don't need it as much as reviewers/verifiers do, while getting no configurable, auditable way to route execution to a cheaper tier without also risking silent correctness regressions that nothing catches.

## Proposal

Fix the inversion and give it a config surface, a dynamic emission path, and a two-rung escalation ladder, scoped as a delta to the **existing `instruction-contracts` capability** (H1, no new-capability marker), with clearly labeled cross-capability scope notes into `adaptive-workflow-tier-selection` where the escalation ladder's workflow rung reuses existing machinery.

**(1) Fix the inversion in agent-file defaults.**
Planning agents — `metta-proposer`, `metta-specifier`, `metta-researcher`, `metta-architect`, `metta-planner`, and `metta-product` — MUST default to inherit/top-tier model (remove or set to `inherit` the `model:` frontmatter key currently pinning them to `sonnet`; add `metta-product` to the planning cohort even though it currently has no `model:` key, to make the "planning agents never get the cheap tier" rule explicit and complete). `metta-reviewer` and `metta-verifier` MUST NEVER be downgraded by any profile, under any configuration — this is a hard rule, not a default that a profile can override, because they are the safety net that makes cheap execution tolerable at all. `metta-executor` is the only agent role eligible for the cheap tier, and only when a models profile and workflow tier say so.

**(2) Config surface: a `models` profile in `.metta/config.yaml`.**
Add a Zod-validated `models` section to `ProjectConfigSchema` (`src/schemas/project-config.ts`) supporting either a named profile (e.g. `quality` / `balanced` / `budget`) or an explicit per-role map with per-workflow-tier executor entries. The schema MUST default to the current behavior — every role inherits the session model — so that a project with no `models` key in `.metta/config.yaml` observes zero behavior change. The schema MUST make it structurally impossible to assign a non-inherit/non-top model to `reviewer` or `verifier` roles (validation-time rejection, not a documentation-only convention).

**(3) Dynamic model emission through the instruction contract — not frontmatter templating.**
Extend `instruction-generator.ts`'s `InstructionOutput.agent` block to carry a computed `model` field, derived from the resolved `models` profile in `.metta/config.yaml` **and** the active change's workflow tier (from `adaptive-workflow-tier-selection`'s `trivial` / `quick` / `standard` / `full` classification). For `trivial`/`quick`-tier changes, an eligible `executor` invocation resolves to the profile's cheap-executor model; for `standard`/`full` tier, or for any role other than `executor`, it resolves to inherit/top-tier. This computation happens **per instruction-generation call**, not by editing agent-file frontmatter — the agent template files stay a single, tier-independent source of truth for persona/tools/rules, and `model` is layered on dynamically. Skills' documented agent-execution pattern (the `Agent(subagent_type: "...", ...)` call convention shown in workflow skills like `metta-execute/SKILL.md`) MUST be extended to read the emitted `model` field from `metta instructions` output and pass it through to the `Agent` tool's per-invocation model parameter. Model values follow Claude Code's agent `model` field vocabulary as verified in research (`sonnet` / `opus` / `haiku` / `inherit`, plus confirmation of whether arbitrary model IDs are accepted) — this vocabulary check MUST be done against current Claude Code docs before the spec fixes allowed values, per the project's research-discipline rule.

**(4) Two-rung escalation ladder — first-class spec requirements, not an afterthought.**
- **Rung 1 — model escalation (new machinery, owned by this capability).** When a cheap-tier executor invocation produces an executor STOP/deviation report, or a subsequent verification run FAILs against a cheap-executor change whose scope stayed within its original tier (no file-count overflow), the affected task or fix MUST be re-run at the top-tier model. This is a model-only re-run — it does not by itself trigger a workflow-tier change.
- **Rung 2 — workflow escalation (existing machinery, reused not duplicated).** When the triggering signal is scope overflow (the change's file count grows past its original tier's boundary), the **existing** `adaptive-workflow-tier-selection` intent-time and post-implementation upscale machinery handles it, unmodified. Because workflow escalation raises the effective tier, it MUST bring top-tier planning agents with it automatically (via the same per-tier resolution in item 3) — and the escalated re-run MUST re-check tier so any retroactive stories/spec obligations that fire at higher tiers still fire. This proposal notes this cross-capability dependency explicitly rather than re-implementing tier upscaling inside `instruction-contracts`.
- **Signal discrimination.** STOP/deviation report or verify-FAIL where scope stayed in-tier → Rung 1 (model escalation only). File-count overflow past the tier boundary → Rung 2 (workflow escalation, which subsumes model escalation for planning agents on the new tier).

**(5) Observability: escalation audit log and escalation-rate metric.**
Every model-escalation event (Rung 1) MUST be recorded with, at minimum: the task/fix identifier, the from-model, the to-model, and the triggering signal (STOP/deviation report vs. verify-FAIL). `metta progress` MUST compute and report an escalation-rate metric (proportion of cheap-tier executor invocations that were subsequently escalated to top-tier), in both human-readable and `--json` output, following the same reporting pattern `adaptive-workflow-tier-selection` already establishes for the ceremony-commit-ratio metric (`spec/specs/adaptive-workflow-tier-selection/spec.md`, "ceremony-commit ratio" requirement). This makes the cheap-first bet empirically checkable: a high escalation rate signals the savings are illusory and the profile should be tightened.

**Honest residual, spec'd explicitly rather than hidden.** A cheap executor that produces plausible-but-wrong code *without* deviating (no STOP report) and that a verification run does not catch until a later phase is not caught by Rung 1 at all — it is caught only by the top-tier verifier one phase later, same as it would be caught today, and is handled by the existing fix-loop. The escalation-rate metric prices this risk indirectly (a low escalation rate does not, by itself, prove the cheap tier is safe — it proves STOP/FAIL-driven escalation is rare) but the spec MUST NOT claim Rung 1 catches silent wrong-but-plausible output.

## Impact

- `src/templates/agents/metta-architect.md`, `metta-planner.md`, `metta-proposer.md`, `metta-researcher.md`, `metta-specifier.md` — remove/change `model: sonnet` to inherit-equivalent.
- `.claude/agents/metta-architect.md`, `metta-planner.md`, `metta-proposer.md`, `metta-researcher.md`, `metta-specifier.md` — deployed copies re-synced to stay byte-identical with the templates (template+deployed byte-identity constraint applies to any frontmatter change).
- `src/schemas/project-config.ts` — new `models` config schema (profile or explicit per-role/per-tier map), Zod-validated, `strict()`, defaulting to current all-inherit behavior; `ProjectConfigSchema` gains an optional `models` field.
- `src/context/instruction-generator.ts` — `InstructionOutput.agent` gains a computed `model` field; `generate()` gains the profile+tier resolution logic (reads resolved config and the change's current workflow tier).
- `src/cli/commands/instructions.ts` — consumes/passes through the new `model` field in emitted instruction output.
- `.claude/skills/*/SKILL.md` (at minimum `metta-execute`, and any other skill documenting the `Agent(subagent_type: "...", ...)` invocation pattern) — documented pattern extended to read and pass the emitted `model` field into the `Agent` tool call.
- New audit-log write path for model-escalation events (task/fix id, from-model, to-model, trigger signal) — persisted via the existing state-store filesystem/`StateStore` conventions (`.metta/` state), Zod-validated on write per project convention.
- `metta progress` command/reporting path — gains an escalation-rate metric in both human-readable and `--json` output, alongside the existing ceremony-commit-ratio metric.
- `spec/specs/instruction-contracts/spec.md` — primary spec delta target (H1).
- `spec/specs/adaptive-workflow-tier-selection/spec.md` — cross-capability scope note describing how Rung 2 workflow escalation interacts with model routing (planning agents on the upscaled tier, retroactive-obligation re-check); direct edits only if the existing upscale requirements do not already cover "re-check tier on escalated re-run" — this is a research question to resolve during spec authoring, not assumed here.
- No changes to `metta-executor.md`, `metta-reviewer.md`, `metta-verifier.md`, `metta-product.md`, `metta-discovery.md`, `metta-constitution-checker.md`, `metta-skill-host.md` frontmatter beyond what item (1) requires (adding `metta-product` to the "never downgrade below inherit for planning" set — it currently has no `model:` key and needs none, since absence already means inherit).
- Projects with no `models` key configured in `.metta/config.yaml` MUST observe no behavior change — this is a hard compatibility requirement, not best-effort.

## Out of Scope

- Changing the reviewer or verifier model under any profile configuration, ever — this is a hard rule enforced at the schema level, not a policy that could be relaxed by a future profile.
- Publishing the package to npm.
- Second-project dogfooding of the model-routing feature.
- Per-model cost accounting or dollar-cost tracking beyond the escalation-rate metric itself (no token-cost-to-dollars conversion, no per-provider billing integration).
- Re-implementing or duplicating any part of `adaptive-workflow-tier-selection`'s intent-time or post-implementation upscale machinery — Rung 2 reuses it as-is; only a cross-capability scope note (and, if genuinely required after research, a minimal direct edit) is in scope here.
- Building new model-eligibility logic for any agent role beyond `executor` — planning agents and `reviewer`/`verifier` are fixed at inherit/top-tier by this change, not made independently configurable per role beyond the profile/tier axis described above.
- Solving the "honest residual" case (silent wrong-but-plausible cheap-executor output with no STOP and no immediate verify-FAIL) with new detection machinery — it remains handled by the existing fix-loop, and is priced, not eliminated, by the escalation-rate metric.
