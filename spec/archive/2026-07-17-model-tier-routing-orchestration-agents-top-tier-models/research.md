# Research: model-tier-routing-orchestration-agents-top-tier-models

## Decision:

Adopt the Claude Code-documented alias vocabulary (`sonnet` / `opus` / `haiku` / `fable` / `inherit`) for the `models` config, deferring free-form full model IDs. Shape the schema as one optional `models` object on `ProjectConfigSchema` with an optional named `profile` shorthand, an optional explicit `executor: { trivial?, quick? }` map, and **structurally present but narrowly typed** `reviewer`/`verifier` keys (`z.literal('inherit').optional()`) — keys exist so misconfiguration is a named Zod field error, not a silently stripped unknown key. Resolve `model` inside `InstructionGenerator.generate()`, reusing the `workflow` tier string already threaded from `instructions.ts` (no new tier-lookup path needed). Record Rung-1 escalations as a **new, separately-named** array field, `model_escalations`, on `ChangeMetadataSchema` — not reusing the existing `escalation` (singular) field, which already means something unrelated (a declined intent-time downscale record from `adaptive-workflow-tier-selection`). Compute the escalation-rate metric with an archive-scanning helper that mirrors `getArtifactsPerSmallChange`'s exact pattern, wired into `metta progress` alongside the existing ceremony metrics.

### Approaches Considered

**1. Model vocabulary — alias enum vs. free-form string vs. hybrid.**
Claude Code's subagent frontmatter `model` field documents exactly four aliases plus two other forms: "`sonnet`, `opus`, `haiku`, `fable`, a full model ID (for example, `claude-opus-4-8`), or `inherit`. Defaults to `inherit`."[^1] The same page states a per-invocation `model` parameter also exists: "When Claude invokes a subagent, it can also pass a `model` parameter for that specific invocation," and gives the resolution order — `CLAUDE_CODE_SUBAGENT_MODEL` env var → per-invocation parameter → subagent frontmatter → main conversation's model.[^1] The docs do not publish a *separate*, narrower vocabulary for the per-invocation parameter; by construction it accepts the same values as frontmatter (aliases, full IDs, `inherit`), since the resolution chain treats it as an equal-priority substitute for the frontmatter value. This session's own Agent-tool schema exposes `model: sonnet|opus|haiku|fable` as an enum with no `inherit`/full-ID choice visible in that surface — consistent with, not contradictory to, the docs: `fable` is confirmed as a real documented alias (not a tool-schema idiosyncrasy), and the narrower enum reflects that the *invocation-time* UI likely only surfaces aliases, while `inherit`/full-ID remain valid but are the implicit default / an advanced form not exposed as enum choices in that particular tool description.
- Option A — accept the full documented vocabulary (aliases + full IDs + `inherit`) as free-form strings validated only by a regex. Rejected: full model IDs churn every release; a regex can't distinguish "cheap" from "top-tier," which the safety-net requirement depends on, and "no unvalidated state writes"/"typed error identifying invalid value" favors a closed enum over pattern-matching.
- Option B — closed Zod enum of exactly `['sonnet', 'opus', 'haiku', 'fable', 'inherit']`. Matches the "Model Vocabulary Validated At Config Load" requirement's rejection semantics precisely (`z.enum` gives a typed, field-naming error on any other string) and keeps cheap-vs-top-tier classification decidable at schema-authoring time (`haiku` is cheap; the rest are top-tier/inherit).
- Option C — Option B plus an escape hatch accepting arbitrary full model IDs via a second schema branch. Deferred, not rejected outright: full-ID passthrough is legitimate per docs but adds an unenumerable trust boundary (any string could be typed in) right where the safety-net immunity depends on knowing "is this a cheap model." Recommend Option B for this change and note the full-ID case as a documented deferral, matching the intent's instruction to "confirm whether arbitrary model IDs are accepted" without being obligated to support them structurally on day one.

**2. Config schema shape — named profiles only vs. explicit role/tier map only vs. both.**
`ProjectConfigSchema` (`src/schemas/project-config.ts:67-85`) is a `.strict()` top-level object with several `.strict()` sub-objects, all optional, each with `.default({})` or field-level `.optional()`/`.default()` — the additive-optional-key pattern this change must follow.
- Option A — named profiles only (`profile: 'quality'|'balanced'|'budget'`). Smallest schema surface, but the spec's "Model Vocabulary Validated At Config Load" and "Safety-Net Immunity" scenarios require validation errors that *name the offending field* (`reviewer`, `verifier`) when a user attempts a downgrade — impossible if the schema only ever accepts a profile name string, since there is no field path to misconfigure.
- Option B — explicit per-role/per-tier map only, no named-profile shorthand. Satisfies the safety-net requirement cleanly (keys exist, are validated) but intent.md and US-2 explicitly require the named-profile convenience form ("declare a `models` profile... e.g. quality/balanced/budget") — dropping it contradicts accepted stories.
- **Option C (recommended)** — both, as one schema: `profile` optional shorthand, `executor: { trivial?, quick? }` optional explicit override, and `reviewer`/`verifier` present as `z.literal('inherit').optional()`. This reconciles the apparent tension the task raised ("keys exist but only accept inherit" vs "don't exist at all"): the *representable role-key set* requirement (spec scenario "The configuration schema exposes no planning-cohort role key") is satisfied because `reviewer`/`verifier`/`executor` are the only three keys present and no planning-cohort name (`proposer`, `specifier`, etc.) is representable at all — while `reviewer`/`verifier` specifically are typed to accept *only* `'inherit'`, so any attempt to set them to `'haiku'` (or anything else) fails `z.literal` validation with a Zod issue at path `models.reviewer` naming the invalid value, exactly matching US-3's "Zod validation rejects it with an error identifying the offending role" and the "no representable profile shape can express a downgraded reviewer or verifier" independent test criterion. Profile names resolve to a hardcoded internal executor-tier map in code (not new schema surface); an explicit `executor` block, if present, is applied on top. No `models` key at all → every resolution falls through to `inherit`, satisfying the hard zero-behavior-change compatibility requirement independent of any schema `.default()`.

**3. Resolution point — inside `InstructionGenerator.generate()` vs. in `instructions.ts` before calling it vs. a new standalone resolver module.**
`instructions.ts` already resolves `metadata.workflow` (the tier string — workflow YAML files are literally named `quick.yaml`/`standard.yaml`/`full.yaml`, and `ComplexityScoreSchema.recommended_workflow` uses the identical `trivial|quick|standard|full` enum, confirming `metadata.workflow` **is** the tier, not a separate lookup) and already passes it into `InstructionGenerator.generate({ ..., workflow: metadata.workflow, ... })` (`src/cli/commands/instructions.ts:64-79`, `src/context/instruction-generator.ts:50-60`). `InstructionOutput.agent` currently emits only `{ name, persona, tools, rules }` (`instruction-generator.ts:13-18`) with no `model` field, and `loadAgentDefinition`/`AgentFrontmatterSchema` (`src/agents/agent-registry.ts`, `src/schemas/agent-definition.ts`) parse no `model:` frontmatter key at all today — the registry is a pure name/persona/tools loader.
- Option A — resolve in `instructions.ts` before calling `generate()`, passing a precomputed `model` string into the params object. Rejected: `instructions.ts` already delegates all context/template computation to `InstructionGenerator`; splitting model resolution out to the caller breaks the "one generation call, one place agent identity is assembled" shape and would require `instructions.ts` to know agent-role semantics (which names are planning-cohort vs. executor) that the generator, not the CLI command, should own.
- Option B (recommended) — resolve inside `generate()`, using the already-threaded `params.workflow` (tier) plus a new `params.modelsConfig` (or equivalent) argument and the already-known `agentName`/`params.agent.name`. This is a pure additive change: no new args need flow through `instructions.ts` beyond passing the loaded config's `models` section, and `agent.model` slots into the existing return object next to `name`/`persona`/`tools`. `agent-registry.ts`/`AgentFrontmatterSchema` need **no** change — model is computed dynamically, not parsed from agent-file frontmatter, which is exactly what the proposal requires ("agent template files stay a single, tier-independent source of truth for persona/tools/rules, and `model` is layered on dynamically").
- Option C — a new standalone `model-resolver.ts` module, called from `generate()`. Reasonable for testability (pure function, easy unit tests independent of `ContextEngine`/`TemplateEngine`); recommend as an implementation detail nested under Option B rather than a competing approach — keeps `generate()`'s existing responsibilities intact while making the resolution logic itself unit-testable in isolation, mirroring how `ceremony-metrics.ts` sits beside `progress.ts` rather than being inlined into it.

**4. Escalation record design — reuse the existing `escalation` field vs. a new field vs. a separate log file.**
`ChangeMetadataSchema` (`src/schemas/change-metadata.ts:47-73`) already has a singular, optional `escalation: EscalationSchema` field (`from_tier`, `to_tier`, `justification`, `timestamp`) — but per `spec/specs/adaptive-workflow-tier-selection/spec.md:460-487`, this field means something specific and unrelated to Rung-1: it is written by `metta complete intent` when an intent-time **downscale offer was declined** (change stays on a tier above its scored recommendation). Reusing this field for Rung-1 model-escalation events would conflate two different event types under one name and one singular (non-array) slot — the existing field is a single snapshot decision, not an append-only log, and Rung-1 needs multiple records per change over its lifetime (US-4/US-6 imply repeatable, countable events for the rate metric).
- Option A — reuse `escalation`, overloading its meaning or repurposing it into an array. Rejected: breaks the deployed `adaptive-workflow-tier-selection` capability's existing scenarios (`schema_accepts_populated_escalation`, `escalation_recorded_on_locked_keep`, etc.), and conflates two audit concerns with different triggers, owners, and cardinalities under one identifier — directly against the project's "no string literal templates" and general clarity conventions, and a likely source of future confusion given both concepts now coexist in the same capability neighborhood.
- Option B (recommended) — a new, distinctly-named optional array field, `model_escalations: z.array(ModelEscalationRecordSchema).optional()`, on `ChangeMetadataSchema`, defaulting to absent (same "legacy files parse unchanged" guarantee the existing `escalation` field already establishes at `spec.md:460`). Each record carries `task_id`/`fix_id`, `from_model`, `to_model`, `trigger` (`'stop_deviation' | 'verify_fail'`), and `timestamp` — mirroring the shape and Zod-validated-on-write discipline of `EscalationSchema` itself and of `artifact_timings`/`artifact_tokens` (both already `z.record(...).optional()` fields written via `ArtifactStore.updateChange`, which round-trips through `StateStore.write` for schema validation before persistence — the same path this change should use, keeping "no unvalidated state writes" intact). This is written by the orchestrator-driven skill/CLI path (the orchestrator detects STOP/verify-FAIL per the skill contract and records the escalation), not computed retroactively.
- Option C — a separate audit-log file (e.g. `.metta/model-escalations.yaml`) outside `.metta.yaml`. Rejected as unnecessary indirection: `.metta.yaml` (`ChangeMetadataSchema`) is already the single per-change state file read by `ArtifactStore`, `progress.ts`, and `ceremony-metrics.ts`; a second file adds a second read/write path and a second migration surface for no benefit, when an optional array field is fully additive and archived alongside the rest of the change's metadata (so `metta progress`'s archive scan — see below — needs no new directory convention).

For the escalation-rate metric, `getArtifactsPerSmallChange` (`src/util/ceremony-metrics.ts:59-89`) is the direct pattern to mirror: it scans `${specDir}/archive/<entry>/.metta.yaml` via `StateStore.read(..., ChangeMetadataSchema)`, skips entries with missing/invalid metadata rather than throwing, and returns `null` (not `0`) when the filtered set is empty. A parallel `getModelEscalationRate` should scan both active (`ctx.artifactStore.listChanges()` + `getChange`) and archived changes for `model_escalations` arrays plus a count of cheap-tier executor invocations (derivable from `model_escalations` denominators or a companion counter), returning `null` for "no cheap-tier invocations recorded" (rendered as the spec's required "explicit no-data indicator") versus `{ rate: 0, ... }` for "recorded invocations, zero escalated." `progress.ts` already threads exactly this null-vs-zero distinction for `ceremonyRatio`/`artifactsPerSmall` in both its `--json` (`ceremony_commit_ratio`, `artifacts_per_small_change` fields, `progress.ts:90-91`) and human-readable (`progress.ts:163-174`) branches — the escalation-rate metric slots into the same two branches beside them.

**5. Skill pass-through.**
`grep` across `.claude/skills/*/SKILL.md` confirms the `Agent(subagent_type: "...", ...)` invocation convention appears in `metta-execute/SKILL.md` (executor spawns, `SKILL.md:36-45`), and in `metta-quick/SKILL.md` for executor, reviewer, and verifier spawns (`SKILL.md:77-187`) — none currently pass a `model` argument. `metta-execute/SKILL.md`'s "Deviation Rules" section (STOP on >10-line blocker or wrong design) is exactly the Rung-1 STOP-report trigger point where the orchestrator, per the skill contract, both re-invokes with `model: <resolved top-tier value>` and records the escalation. Since the per-invocation `model` parameter is documented as a first-class Agent/Task tool input with the same accepted vocabulary as frontmatter,[^1] extending these `Agent(...)` call examples to read `model` off `metta instructions --json`'s emitted `agent.model` field and forward it verbatim is a documentation-only change to the skill files, not a new capability.

**6. Frontmatter cleanup — confirmed inventory.**
`grep -rn "model: sonnet" src/templates/agents/ .claude/agents/` returns exactly ten matches across five short names, template and deployed copies both present for each: `metta-proposer.md`, `metta-planner.md`, `metta-researcher.md`, `metta-architect.md`, `metta-specifier.md`. `metta-product.md` has no `model:` key in either location today (confirmed absent from the grep results), matching intent.md's description — it needs no new key, only inclusion in the "never below inherit" *rule*, not a file edit.

**7. Test surface.**
`tests/instructions-agent-registry.test.ts` drives the CLI via `tsx` against a temp project fixture with a real `.metta/config.yaml` and asserts on `metta instructions --json` output shape sourced from agent files — the direct harness to extend for `agent.model` assertions across profile/tier fixture combinations. `tests/config-loader.test.ts` uses `mkdtemp` + `ConfigLoader` fixtures for project/global merge behavior — the pattern for `models`-key validation-rejection tests (US-3's reviewer/verifier rejection cases) and the "no `models` key → unchanged output" compatibility case. `tests/progress-ceremony-metrics.test.ts` and `ceremony-metrics.test.ts` establish the archive-fixture-scanning pattern (`StateStore` writes into a temp `archive/<name>/.metta.yaml`, then assert on the computed metric) to mirror for `getModelEscalationRate`. `tests/agent-registry.test.ts` covers `loadAgentDefinition` directly and should gain coverage confirming it still parses cleanly with `model:` frontmatter absent from planning-cohort files (a negative-presence assertion, not a new capability in the loader itself, since model resolution stays out of agent-file parsing per Option B in point 3).

### Rationale

The vocabulary decision (alias enum, full-ID deferred) is the one point where the intent explicitly demanded doc-grounding before the spec could fix allowed values, and Claude Code's docs give an unambiguous, quotable answer[^1] — closing that question. The schema shape (Option C, §2) is the one structural design that simultaneously satisfies three separately-stated constraints that look contradictory at first glance: "smallest schema," "keys exist so a validation error can name them," and "no planning-cohort key at all" — by scoping the representable key set to exactly `{profile, executor, reviewer, verifier}` and typing `reviewer`/`verifier` to `z.literal('inherit')` rather than omitting them. The resolution-point decision (Option B, §3) costs nothing beyond one new optional constructor argument, because `instructions.ts` already resolves and threads the tier value the resolution logic needs — no new data plumbing, no new file reads. The escalation-record decision (Option B, §4) was the one surprising finding: a field named `escalation` already exists on `ChangeMetadataSchema` and already means a *different, currently-shipped* concept (declined-downscale audit, not model-tier audit) — silently overloading it would have been a correctness bug hiding in a plausible-looking reuse, caught only by reading `adaptive-workflow-tier-selection`'s spec text directly rather than inferring from the field name.
