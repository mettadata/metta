# fix-harden-metta-guard-bash-trust-model-unify-all-blocked — User Stories

## US-1: Forgeable inline token grants nothing

**As a** metta maintainer defending the guard hook against a would-be bypass (an AI orchestrator that retypes the legacy inline prefix)
**I want to** have the guard hook reject `METTA_SKILL=1 metta <blocked-subcommand>` typed directly in a session with no active skill, for all twelve blocked subcommands
**So that** no plain-text token an orchestrator can author in a Bash command string ever grants state-mutating access to `.metta/` state or spec files outside a skill's authored contract
**Priority:** P1
**Independent Test Criteria:** Feeding the hook a synthetic PreToolUse event with `command: "METTA_SKILL=1 metta finalize"` (and likewise for `complete`, `refresh`, `import`, `init`, `fix-gap`) and no trusted `agent_type` or session token yields a deny decision whose message names the matching `/metta-*` skill.

**Acceptance Criteria:**
- **Given** a session with no active skill and no valid session token on disk **When** the orchestrator runs `METTA_SKILL=1 metta finalize` (or any of the other five formerly prefix-only subcommands) **Then** the hook blocks the call and the guidance message points to the sanctioned skill entry point
- **Given** a fabricated token file written by the orchestrator with a guessed value **When** a Tier-2 subcommand is invoked **Then** the hook detects the mismatch, rejects the call, and records the rejection reason in `guard-bypass.log`
- **Given** the change has shipped **When** the hook source is inspected **Then** the `!inv.skillBypass` legacy fallback for non-enforced subcommands is gone and no code path authorizes a call based solely on inline command text

---

## US-2: Main-session lifecycle skills keep working

**As an** AI orchestrator running `metta-next`, `metta-plan`, `metta-execute`, or `metta-verify` in the main session (unforked by design)
**I want to** run `metta complete`, `metta finalize`, and `metta instructions` through the sanctioned Tier-2 session-token mechanism my skill contract acquires for me
**So that** the main-session orchestration pattern the lifecycle skills depend on continues to work end-to-end without interactive friction or a lockout caused by the missing `agent_type` those unforked skills structurally lack
**Priority:** P1
**Independent Test Criteria:** A synthetic PreToolUse event for `metta complete` issued after the skill-launch token step (valid, unexpired token on disk under `.metta/scratch/`) is allowed by the hook, and the token is rotated/consumed on that match so a verbatim replay of the same value is rejected.

**Acceptance Criteria:**
- **Given** a lifecycle skill has performed its token-acquisition step (CLI-issued, not typed by the orchestrator) **When** the skill body runs a Tier-2 subcommand such as `metta complete` or `metta finalize` **Then** the hook validates the token and allows the call without prompting the user
- **Given** a token that has been consumed or has exceeded its TTL **When** the same Tier-2 subcommand is retried with the stale value **Then** the hook rejects the call, so a leaked token cannot be replayed indefinitely
- **Given** the token issuance step **When** the token value is inspected **Then** it was generated by the `metta` CLI (server-side), never authored inside the orchestrator's command text

---

## US-3: Fork-tier enforcement is unchanged

**As an** AI orchestrator invoking fork-dispatched skills (`propose`, `quick`, `auto`, `ship`, `issue`, `fix-issue`)
**I want to** have Tier-1 enforcement — trusted `agent_type` requirement, background-Bash-from-fork rejection, and audit logging — behave exactly as it does today
**So that** hardening Tier 2 does not regress the fork-boundary protections that shipped in `fix-metta-guard-bash-allows-ai-orchestrators-bypass-skill` and the recent process-group fixes
**Priority:** P1
**Independent Test Criteria:** Replaying the existing Tier-1 hook scenarios as synthetic PreToolUse events — enforced subcommand with `agent_type: "metta-skill-host"` (allow), without it (deny), and with `run_in_background: true` from a fork (deny) — produces identical decisions and JSON-line audit entries before and after the change.

**Acceptance Criteria:**
- **Given** a PreToolUse event with `event.agent_type` starting with `metta-` **When** a `SKILL_ENFORCED_SUBCOMMANDS` member is invoked **Then** the call is allowed, exactly as before the change
- **Given** a PreToolUse event lacking a trusted `agent_type` **When** an enforced subcommand is invoked **Then** the call is denied and a JSON-line entry is appended to `guard-bypass.log` in the existing format (extended at most, never removed)
- **Given** a Bash call with `run_in_background: true` originating from a forked skill context **When** the hook evaluates it **Then** the rejection introduced this week still fires unmodified

## US-4: Complete migration with no dangling legacy prefixes

**As a** metta maintainer shipping this change
**I want to** migrate every `METTA_SKILL=1` call site — roughly 154 lines across the 15 `SKILL.md` files in both `.claude/skills/` and `src/templates/skills/` — to the new token mechanism within this same change, keeping deployed and template copies byte-identical
**So that** no skill is left issuing a prefix the hook no longer honors (which would silently break that skill's contract), and the retired token leaves no half-migrated state behind
**Priority:** P1
**Independent Test Criteria:** `grep -r "METTA_SKILL=1" .claude/skills/ src/templates/skills/ .claude/hooks/ src/templates/hooks/` returns zero matches after the change, `diff` between each deployed/template pair is empty, and `node --check` passes on both hook copies.

**Acceptance Criteria:**
- **Given** the change is complete **When** the repository is searched for `METTA_SKILL=1` in skill and hook files **Then** zero call sites remain in either the deployed or template copies
- **Given** the 15 affected skill pairs **When** each `.claude/skills/` file is compared with its `src/templates/skills/` counterpart **Then** the copies are identical, and the same holds for the two hook copies
- **Given** the retired inline prefix **When** planning resolves the `config-loader.ts` question **Then** the `METTA_SKILL` special case in the `RESERVED` set is either removed or retained with an updated comment documenting the transitional reason — never left as an unexplained workaround
- **Given** any edit to the hook file **When** the executing session issues its next Bash call **Then** `node --check` has already been run on both hook copies, since the hook gates its own author's future calls

## US-5: Two-tier trust model is documented

**As a** metta maintainer or future contributor reading the guard hook or CLAUDE.md
**I want to** find an accurate description of the two-tier trust model — Tier 1 fork-dispatched commands authorized by `agent_type`, Tier 2 main-session commands authorized by the rotating session token — in the hook's header comment and CLAUDE.md's workflow section
**So that** the rationale for why the two tiers exist and why each signal is non-forgeable is discoverable without reverse-engineering the hook source, and future changes do not accidentally reintroduce a plain-text trust token
**Priority:** P2
**Independent Test Criteria:** The `metta-guard-bash.mjs` header comment (both copies) and CLAUDE.md's "How to work" section each describe both tiers, their subcommand membership, and the emergency bypass, with no remaining reference to the retired "Primary/Secondary/Emergency bypass" `METTA_SKILL=1` model.

**Acceptance Criteria:**
- **Given** the shipped hook file **When** its header comment is read **Then** it explains both tiers, which subcommands belong to each, and why each trust signal cannot be forged from Bash command text
- **Given** CLAUDE.md's "How to work" / workflow section **When** a reader consults it **Then** it documents the two-tier model and notes that the `.claude/settings.local.json` hook-disable escape hatch remains the emergency bypass for humans and CI
- **Given** the retired model **When** documentation is searched for the old bypass description **Then** no doc still instructs anyone to type `METTA_SKILL=1` to authorize a blocked subcommand
